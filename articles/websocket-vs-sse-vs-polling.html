WebSocket vs Server-Sent Events vs Long Polling: что когда использовать

27 октября 2026 • 10 мин чтения
Поделиться:

Реал-тайм в вебе — это когда данные приходят в браузер без перезагрузки страницы: чаты, уведомления, обновления курсов, статусы заказов. Чтобы это работало, у тебя есть три основных технологии: long polling, Server-Sent Events (SSE) и WebSocket. В этой статье разберём, чем они отличаются и что выбирать.

Если ты не очень в HTTP — загляни в основы HTTP и детальный разбор WebSocket. Без воды — только то, что влияет на выбор.

Что такое real-time в вебе

Классический HTTP работает по модели запрос-ответ: браузер просит, сервер даёт. Если сервер хочет сам отправить что-то в браузер — он не может: HTTP не поддерживает «инициативу сервера». Поэтому придумали обходные пути.

Long polling — браузер делает запрос, сервер держит его открытым, пока не появится новое сообщение, и только тогда отвечает. Браузер тут же открывает новый запрос. SSE — сервер держит одно соединение открытым и шлёт события потоком. WebSocket — отдельный протокол поверх TCP, где сервер и клиент общаются в обе стороны свободно.

Long Polling: старая добрая классика

Long polling — самый простой вариант. Браузер делает обычный HTTP-запрос к серверу, сервер не отвечает сразу, а ждёт появления данных. Когда данные появляются — отвечает. Браузер тут же делает новый запрос. Цикл повторяется.

Плюсы: работает везде, даже в старых браузерах, легко реализуется на любой серверной технологии без специальных библиотек. Минусы: много лишних запросов, накладные расходы на handshake, задержки между получением ответа и новым запросом (gap).

// Клиентский long polling
async function poll() {
  while (true) {
    try {
      const res = await fetch('/api/updates');
      const data = await res.json();
      handleEvent(data);
    } catch (e) {
      await new Promise(r => setTimeout(r, 1000));
    }
  }
}
poll();

В 2026 году long polling почти не используют в новых проектах — SSE и WebSocket делают то же самое лучше. Но он остаётся аварийным вариантом для старых прокси и корпоративных сетей, где WebSocket не проходит.

Иногда long polling — лучший выбор даже в 2026 году. Например, если у тебя нечастые события (раз в минуту) и простая серверная инфраструктура — нет смысла усложнять код SSE или WebSocket. Long polling с лимитом времени запроса (например, 30 секунд) даёт простую и работающую систему без лишних абстракций.

Server-Sent Events: простой и достаточный

SSE — это способ получить постоянный поток событий с сервера в браузер. Соединение держится открытым, сервер шлёт сообщения в формате text/event-stream. Браузер автоматически восстанавливает соединение при обрыве. Поддержка встроена через объект EventSource — никаких библиотек не нужно.

SSE идеален для односторонней коммуникации: уведомления, ленты новостей, обновления статусов, логи в реальном времени. Большая часть real-time веба на самом деле односторонняя — и SSE там идеально подходит.

// Клиент
const es = new EventSource('/api/events');
es.onmessage = (e) => {
  const data = JSON.parse(e.data);
  console.log('Получено:', data);
};
es.onerror = () => console.log('Реконнект автоматический');
# Сервер (Python, FastAPI)
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

async def event_stream():
    while True:
        yield "data: hello\n\n"

@app.get("/api/events")
async def events():
    return StreamingResponse(
        event_stream(),
        media_type="text/event-stream"
    )

Минусы SSE: только односторонний (сервер к клиенту), лимит в 6 соединений на домен в HTTP/1.1 (с HTTP/2 это снимается), не работает через некоторые старые прокси. Также SSE не работает в IE — но в 2026 году это уже не проблема.

WebSocket: двунаправленный канал

WebSocket — это отдельный протокол поверх TCP. Устанавливается через HTTP-рукопожатие, потом переходит в режим постоянного двунаправленного канала. Сервер и клиент могут слать сообщения в любую сторону в любое время.

WebSocket идеален для чатов, multiplayer-игр, коллаборативных редакторов (Google Docs), стримов котировок в обе стороны, интерактивных досок. Если тебе надо слать данные от клиента к серверу часто и с малой задержкой — WebSocket.

// Клиент
const ws = new WebSocket('wss://api.example.com/ws');
ws.onopen = () => ws.send('hello');
ws.onmessage = (e) => console.log('Получено:', e.data);
ws.onclose = () => console.log('Соединение закрылось');

// Отправка в любой момент
ws.send(JSON.stringify({type: 'ping'}));

Минусы: сложнее в реализации, надо вручную реконнектить, не все прокси и CDN корректно проксируют WS-соединения. Также WebSocket не работает с HTTP/2 мультиплексированием в старых реализациях.

Для production-сценариев WebSocket почти всегда требует дополнительной инфраструктуры: sticky sessions на load balancer, отдельный gateway для управления соединениями, мониторинг активных коннектов. В большой системе с десятками тысяч одновременных клиентов ставят специализированные WS-балансировщики вроде Pushpin или Centrifugo. Они принимают WS от клиентов и делают pub/sub между инстансами приложения.

Что выбрать: практическое руководство

Если тебе нужно просто показать пользователю, что у него новое сообщение — SSE. Это самый недооценённый инструмент: многие выбирают WebSocket «на всякий случай», хотя SSE хватит за глаза. Меньше кода, меньше багов, проще масштабировать.

Если ты делаешь чат с друзьями, где надо слать сообщения в обе стороны — WebSocket. Аналогично для игр и интерактивных досок. Если нужна двусторонняя коммуникация — без WebSocket не обойтись.

Если ты поддерживаешь старый корпоративный софт с прокси, которые режут WS, — оставайся на long polling. Это редкий сценарий, но встречается в больших компаниях с жёсткой сетевой политикой.

Не выбирай WebSocket «на всякий случай». SSE покрывает 70% real-time сценариев с половиной сложности.

Production-нюансы

Масштабирование: long polling и SSE хорошо горизонтально масштабируются через sticky sessions или распределение событий через pub/sub (Redis, Kafka). WebSocket сложнее — нужен gateway вроде Pushpin или специальный WS-балансировщик.

Реконнекты: SSE встроен в браузер. WebSocket надо делать вручную через библиотеку reconnecting-websocket или свою обёртку. Long polling — сам становится реконнектом, если оформить правильно.

Аутентификация: SSE и long polling идёт через обычные HTTP-cookies — всё просто. WebSocket со standard-протоколом не отправляет cookies автоматически, нужно прокидывать токен в первом сообщении или через подзапрос.

Сравни подробно — в статье про WebSocket и HTTP-методы. Если нужна маршрутизация — обзор Nginx.

Типичные паттерны и примеры кода

Реал-тайм в реальных приложениях редко сводится к чистому «слать события». Вокруг вырастают паттерны: авторизация, реконнекты, сердце-биения (heartbeat), масштабирование через pub/sub. Разберём ключевые.

Heartbeat (пинг-понг). Соединение может упасть незаметно для клиента — например, NAT-таблица на роутере устарела. Чтобы это отловить, шлют periodic-пинги. В WebSocket это встроено в протокол (control-фреймы), но часто дублируют на уровне приложения: каждые 30 секунд клиент шлёт «ping», сервер отвечает «pong». Если ответа нет 60 секунд — реконнект.

// Heartbeat на уровне приложения
setInterval(() => {
  if (ws.readyState === WebSocket.OPEN) {
    ws.send(JSON.stringify({type: 'ping'}));
  }
}, 30000);

ws.onmessage = (e) => {
  const msg = JSON.parse(e.data);
  if (msg.type === 'pong') return; // heartbeat ответ
  // обрабатываем реальные сообщения
};

Аутентификация на handshake. В WebSocket токен обычно передают в query-параметре: wss://api.example.com/ws?token=xxx. Это небезопасно для production — токен попадает в логи. Лучший подход: открыть обычный HTTP-запрос для handshake, получить одноразовый ticket, потом подключаться по WebSocket с этим ticket. Подробнее про токены — в статье про JWT.

Pub/sub для масштабирования. Когда у тебя несколько инстансов сервера, нельзя слать события прямо из текущего процесса — другие не узнают. Все инстансы подписываются на Redis/Kafka, и когда любой из них хочет слать событие — публикует в канал. Все инстансы получают и решают, у кого из клиентов подписка на это событие.

Backpressure. Если клиент медленный или сеть плохая, сервер может наваливать события быстрее, чем клиент успевает. Это «backpressure»: надо либо буферизировать, либо дропать, либо сигнализировать вышестоящему сервису о замедлении. WebSocket API даёт ws.bufferedAmount — размер очереди отправки. Если он растёт — пора притормозить.

Idempotency. События могут приходить дважды (из-за ретраев или обрывов). Обработчик должен быть идемпотентным: повторное применение не меняет результат. Для этого используют event ID: каждое сообщение содержит уникальный ID, клиент хранит последние N IDs и игнорирует дубликаты.

Reconnection с backoff. При обрыве не подключайся сразу — сервер может лежать и тысяча клиентов одновременно ударит по нему. Используй экспоненциальный backoff: 1с, 2с, 4с, 8с, 16с, 30с максимум. Это сглаживает нагрузку при массовом реконнекте.

FAQ

Что выбрать для чата?

WebSocket. Чат — двунаправленная коммуникация: пользователь шлёт сообщения и получает от других. SSE не подходит, потому что не может принимать данные от клиента.

Что выбрать для уведомлений?

SSE. Это односторонний сценарий: сервер шлёт уведомления, клиент их слушает. Реализуется в 20 строк кода, работает без библиотек.

SSE работает с HTTPS?

Да, идеально. Если страница открыта по HTTPS, EventSource автоматически использует защиту. Просто указывай относительный URL — браузер всё сделает.

WebSocket работает через Nginx?

Да, с правильной конфигурацией. Nginx поддерживает WebSocket через upgrade-заголовки. Подробнее — в статье про Nginx.

Что быстрее — WebSocket или SSE?

По накладным расходам WebSocket чуть быстрее для частых мелких сообщений, потому что нет HTTP-overhead на каждом сообщении. Для редких событий (раз в секунду и реже) — разница незаметна. SSE компактнее на уровне кода.

Что лучше для стриминга видео?

Ни одно из этого. Для видео используют другие протоколы: HLS, WebRTC, RTMP. WebSocket и SSE — для коротких событий и текстовых сообщений, не для медиа-стримов.

Краткий вывод

В 2026 году выбор real-time-технологии зависит от задачи. Long polling — fallback для старых сетей. SSE — простой и достаточный для односторонних обновлений. WebSocket — для полноценной двусторонней коммуникации. Главное правило: не усложняй. Если SSE достаточно — не тащи WebSocket. Если WebSocket необходим — не пытайся выкрутиться через long polling.

Также помни: real-time — это не только протокол, но и инфраструктура. Реконнекты, heartbeat, аутентификация, масштабирование через pub/sub — всё это надо продумать до продакшна. Напиши простой прототип, погоняй под нагрузкой, и только потом выкатывай. Лучше потратить день на тесты, чем получить отвал в час пик.
