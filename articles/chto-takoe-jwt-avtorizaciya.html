Что такое JWT и как работает авторизация

3 апреля 2026 • 10 мин чтения
Поделиться:

Если ты делаешь бэкенд для веб-приложения или мобильного клиента, рано или поздно упрёшься в вопрос: как понять, что пользователь — это тот, за кого он себя выдаёт? Есть два подхода: сессии на сервере и токены на клиенте. JWT — самый популярный вариант второго.

Зачем вообще авторизация

HTTP — протокол без памяти. Сервер не помнит, что ты залогинился три запроса назад. Значит, при каждом запросе клиент должен как-то подтвердить: «Я — это я».

Есть два способа:

  • Сессии. Сервер хранит состояние: «клиент с ID abc123 — это пользователь Кира». Клиент носит с собой куку с этим ID.
  • Токены. Сервер не хранит состояние. Клиент носит с собой подписанный токен, в котором написано, кто он такой.

JWT — самый распространённый формат токена.

Что такое JWT

JWT (JSON Web Token, произносится «джот») — это строка из трёх частей, разделённых точками:

xxxxx.yyyyy.zzzzz

Три части:

  1. Header — метаданные: тип токена и алгоритм подписи.
  2. Payload — данные (claims): кто пользователь, когда выпущен, до когда действует.
  3. Signature — подпись, которой сервер подтверждает подлинность.

Как выглядит внутри

Header

{
  "alg": "HS256",
  "typ": "JWT"
}

HS256 значит HMAC + SHA-256. Такой алгоритм использует общий секрет: и подписывает, и проверяет один и тот же ключ.

Payload

{
  "sub": "42",
  "name": "Кирилл",
  "role": "admin",
  "iat": 1711900000,
  "exp": 1711903600
}

Поля:

  • sub — subject, ID пользователя.
  • name, role — произвольные данные.
  • iat — issued at, время выпуска (Unix timestamp).
  • exp — expiration, время истечения.

Signature

Берётся header, payload, секретный ключ — и через HMAC-SHA256 вычисляется подпись. Сервер при получении токена делает то же самое и сравнивает. Если хоть один символ изменён — подписи не совпадут, токен отвергается.

JWT не шифрует данные. Header и payload — это просто Base64. Любой может их прочитать. Подпись защищает только от изменения, а не от чтения.

Как это выглядит в коде

На Python с библиотекой PyJWT:

import jwt
from datetime import datetime, timedelta

SECRET = 'очень-секретный-ключ'

def create_token(user_id):
    payload = {
        'sub': user_id,
        'iat': datetime.utcnow(),
        'exp': datetime.utcnow() + timedelta(hours=1)
    }
    return jwt.encode(payload, SECRET, algorithm='HS256')

def verify_token(token):
    try:
        return jwt.decode(token, SECRET, algorithms=['HS256'])
    except jwt.ExpiredSignatureError:
        return None
    except jwt.InvalidTokenError:
        return None

Клиент отправляет токен в заголовке:

Authorization: Bearer eyJhbGciOiJIUzI1NiIs...

Сервер на каждом запросе проверяет: подпись валидна, срок не истёк. Если всё ок — обрабатывает запрос.

Для продакшена обычно берут httpOnly cookie + защиту от CSRF (SameSite, CSRF-токен).

Access и Refresh токены

Возникает проблема: если токен украли, а срок жизни — сутки, злоумышленник сутки имеет доступ. Уменьшать срок жизни до 5 минут неудобно — пользователь будет постоянно перелогиниваться.

Решение — два токена:

  • Access token — короткий, 5–15 минут. Отправляется с каждым запросом.
  • Refresh token — длинный, дни или недели. Хранится на сервере, используется только для получения нового access-токена.

Если access-токен утёк — через 15 минут он перестанет работать. Refresh при этом хранится в httpOnly cookie и обновляется редко.

JWT vs сессии: что выбрать

КритерийСессииJWT
Состояние на сервереЕсть (хранит данные сессии)Нет
МасштабированиеСложнее, нужен общий storeПросто, сервер stateless
Отзыв токенаМгновенныйСложный (нужен blacklist)
МикросервисыТребует общего хранилищаПроще, токен самодостаточен
РазмерМаленькая кукаТокен может быть большим

Ключевая проблема JWT — нельзя мгновенно отозвать токен. Если пользователь разлогинился, а токен живёт ещё 15 минут — он всё ещё работает. Отсюда и появляются blacklist'ы и короткие сроки жизни access-токенов.

Типичные ошибки

  • Слабый секретный ключ. Если ключ secret123 — его подберут брутфорсом. Используй случайные 32+ байта.
  • Хранение пароля в payload. JWT читается всеми — пароль там не место.
  • Игнорирование exp. Сервер обязан проверять срок истечения. Некоторые библиотеки это делают, но перепроверь.
  • Алгоритм none. Есть уязвимость, когда токен подделывают с заголовком "alg": "none". Указывай явный список допустимых алгоритмов.
  • Секрет в клиентском коде. Если секрет попал в JS-бандл — токены подделает любой.
  • Слишком долгий TTL. Полгода живущий токен — приглашение для взломщика.

Когда JWT не нужен

Если у тебя монолитное приложение с сессиями в Redis — сессии часто проще и безопаснее. JWT оправдан, когда:

  • у тебя микросервисы, и токен должен работать в любом из них без обращения к общему store;
  • есть мобильное приложение или SPA, и ты хочешь stateless-авторизацию;
  • нужна интеграция с внешними сервисами (OAuth).
JWT — не «лучший способ авторизации». Это инструмент с конкретными плюсами и минусами. Применяй, когда плюсы перевешивают.

Итог

JWT — это подписанный токен, который несёт в себе данные о пользователе. Сервер не хранит состояние, проверяет только подпись и срок. Удобно для масштабирования, но требует аккуратности: правильный секрет, короткий TTL, пара access + refresh, безопасное хранение на клиенте.
