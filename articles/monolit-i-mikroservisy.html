Монолит и микросервисы — когда что выбирать

5 апреля 2026 • 11 мин чтения
Поделиться:

«Мы переезжаем на микросервисы» — фраза, которую слышал каждый, кто работал в IT-компании. Звучит солидно, но не всегда означает улучшение. Разберёмся, что это и когда оно действительно оправдано.

Монолит: как было раньше

Монолит — это одно приложение, где всё вместе: пользователи, заказы, платежи, уведомления. Один код, одна база данных, один деплой.

Пример структуры:

myapp/
├── users/        # модуль пользователей
├── orders/       # модуль заказов
├── payments/     # модуль оплаты
├── notifications/# модуль уведомлений
└── main.py       # точка входа

Всё запускается одной командой, деплоится одним пакетом, тестируется целиком.

Плюсы монолита

  • Простота. Один проект, один репозиторий, одна сборка.
  • Локальная разработка. Склонировал — запустил — работает.
  • Транзакции. Одна база — можно делать атомарные операции между любыми данными.
  • Нет сетевых задержек. Функции вызываются напрямую, а не через HTTP.
  • Легко отлаживать. Один стектрейс, один лог.

Минусы монолита

  • Масштабируется целиком. Если нагрузка только на оплату — всё равно масштабируешь всё приложение.
  • Один упал — всё упало. Ошибка в модуле уведомлений может положить весь сервис.
  • Растёт и пухнет. Через 3 года кодовая база превращается в «большой шар грязи».
  • Команды мешают друг другу. Все правят один код, релизы ждут друг друга.
  • Долгий деплой. Собрать и задеплоить 500-тысячный монолит — не быстро.

Микросервисы: что это

Микросервисы — это разбиение монолита на независимые сервисы. Каждый сервис:

  • отвечает за свою бизнес-функцию (пользователи, заказы, оплата);
  • имеет свою базу данных;
  • деплоится отдельно;
  • общается с другими по сети (HTTP, gRPC, очереди).

Та же структура, но разбитая:

users-service/       → своя база users-db
orders-service/      → своя база orders-db
payments-service/    → своя база payments-db
notifications-service/ → своя база notifications-db
api-gateway/         → маршрутизация запросов

Каждый сервис — отдельное приложение, отдельный репозиторий, отдельная команда.

Плюсы микросервисов

  • Независимый деплой. Обновление сервиса оплаты не требует пересборки всего.
  • Масштабируется точечно. Большая нагрузка на поиск — масштабируем только поиск.
  • Изоляция сбоев. Упал сервис уведомлений — остальное работает.
  • Свобода технологий. Один сервис на Python, другой на Go, третий на Java.
  • Команды автономны. Каждая команда владеет своим сервисом.

Минусы микросервисов

  • Сложная инфраструктура. Нужны Docker, Kubernetes, service mesh, мониторинг, трейсинг.
  • Сетевые задержки. Вызов по HTTP медленнее, чем вызов функции.
  • Нет общих транзакций. Нельзя просто сделать «списать деньги и создать заказ» — нужны саги, компенсации.
  • Сложная отладка. Один запрос идёт через 5 сервисов — поймай, где упало.
  • Дублирование кода. Общие вещи (аутентификация, логирование) нужно настраивать в каждом.
Микросервисы не упрощают систему. Они переносят сложность из кода в инфраструктуру. Если у тебя и так всё просто — микросервисы сделают сложнее.

Когда монолит лучше

  • Стартап на ранней стадии. Не знаешь ещё, что приживётся, — гибкость важнее масштаба.
  • Небольшая команда. 5 человек не могут обслуживать 10 сервисов.
  • Нет задач по масштабированию. Если 1000 пользователей — монолит справится.
  • Простая предметная область. Блог, лендинг, простое приложение.

Когда микросервисы оправданы

  • Большие команды. 100+ разработчиков в одном монолите — гарантированный хаос.
  • Разные нагрузки на разные части. Один сервис нужен каждому пользователю, другой — раз в час.
  • Разные технологии под задачи. Мachine learning на Python, а API — на Go.
  • Высокие требования к отказоустойчивости. Если падение одного модуля не должно ронять всё.

Промежуточный вариант: модульный монолит

Есть золотая середина — модульный монолит. Это одно приложение, но внутри чётко разделённое на модули с понятными границами.

myapp/
├── users/          # модуль с чётким публичным API
│   ├── api.py
│   └── internal/
├── orders/         # модули не лезут в internals друг друга
│   ├── api.py
│   └── internal/
└── main.py         # собирает всё вместе

Плюсы:

  • Просто, как монолит.
  • Если завтра понадобится — любой модуль легко вынести в отдельный сервис.
  • Нет инфраструктурной боли.

Многие опытные команды советуют начинать именно с этого. Модульный монолит даёт 90% преимуществ микросервисов без 90% их проблем.

Начни с монолита. Если он станет проблемой — разбей. Но не начинай с микросервисов, потому что «это современно».

Что нужно, если всё-таки идёшь в микросервисы

Минимальный набор:

  • Контейнеры. Docker для каждого сервиса.
  • Оркестрация. Kubernetes или хотя бы Docker Compose для локалки.
  • API Gateway. Единая точка входа для клиента.
  • Service discovery. Сервисы должны находить друг друга по имени.
  • Централизованные логи. ELK, Loki, что угодно.
  • Трейсинг. Jaeger, OpenTelemetry — видеть путь запроса через сервисы.
  • Мониторинг. Prometheus + Grafana.
  • CI/CD для каждого сервиса. Автодеплой, автотесты.

Без этого всего микросервисы превращаются в тыкву через месяц.

Итог

Монолит — простой и быстрый старт. Микросервисы — мощная штука, но только при больших командах и серьёзной инфраструктуре. Если ты один или у тебя небольшая команда — модульный монолит покроет все нужды. А про то, как выглядит деплой в таких системах, читай в статье про DevOps и CI/CD.
