Git ветки и слияния — branch, merge, rebase

8 апреля 2026 • 11 мин чтения
Поделиться:

Одна из главных фишек Git — ветки. Ты можешь работать над новой фичей, не ломая основную версию проекта. Если что-то пойдёт не так — просто удалишь ветку. Если получилось — сольёшь в основную.

Если ты ещё не знаешь базовых команд — начни со статьи Git для новичков. Здесь про ветки и слияния.

Что такое ветка

Ветка (branch) — это отдельная линия разработки. По умолчанию в репозитории есть одна ветка — обычно main. Но ты можешь создать сколько угодно дополнительных.

Ветка — это просто указатель на коммит. Не копия файлов, не копия папки. Всего лишь метка. Поэтому создание ветки в Git — мгновенно.

Схематично:

main:    A --- B --- C --- D
                    \
feature:             E --- F

Тут мы от коммита B создали ветку feature, сделали два коммита E и F, а main в это время продолжал жить своей жизнью.

Основные команды

# Посмотреть все ветки (текущая помечена звёздочкой)
git branch

# Создать новую ветку
git branch feature-login

# Переключиться на существующую ветку
git checkout feature-login

# Создать ветку и сразу переключиться (два в одном)
git checkout -b feature-login

# Современный синтаксис (то же самое, но нагляднее)
git switch -c feature-login

# Удалить ветку (если уже слита)
git branch -d feature-login

# Удалить ветку принудительно (если не слита)
git branch -D feature-login

Команда git switch появилась в Git 2.23 как замена checkout для переключения веток. Старый вариант тоже работает, но новый понятнее: switch — про ветки, restore — про файлы.

Как происходит типичная работа

Допустим, ты хочешь добавить форму логина на сайт. Делаешь так:

# Убеждаемся, что мы на main и он актуален
git checkout main
git pull

# Создаём ветку для новой фичи
git switch -c feature-login

# Работаем — пишем код, коммитим
# ... несколько коммитов ...

# Отправляем ветку на GitHub
git push -u origin feature-login

Флаг -u (upstream) связывает локальную ветку с удалённой — потом можно писать просто git push без указания имени.

Дальше на GitHub ты открываешь Pull Request — предложение слить изменения в main. Команда смотрит, обсуждает, комментирует. Если всё ок — мержит.

Merge — слияние веток

Когда работа в ветке закончена, её нужно влить в основную. Это делает команда merge.

# Переключаемся на main
git checkout main

# Вливаем в него ветку feature-login
git merge feature-login

Что произойдёт — зависит от истории.

Fast-forward merge

Если main не менялся с момента создания ветки, Git просто «переставит» указатель main на последний коммит ветки:

До:
main:    A --- B
                \
feature:         C --- D

После:
main:    A --- B --- C --- D

Получается линейная история, и это красиво.

Three-way merge

Если main менялся параллельно, Git создаёт специальный merge-коммит, у которого два родителя:

До:
main:    A --- B --- E
                \
feature:         C --- D

После:
main:    A --- B --- E --- M
                \         /
feature:         C --- D

Коммит M — это и есть merge-коммит. Он говорит: «здесь мы объединили две ветки».

Конфликты и как их решать

Если ты и коллега изменили одну и ту же строку в одном файле — Git не знает, кого выбрать. Это конфликт.

git merge feature-login
# CONFLICT (content): Merge conflict in src/login.js
# Automatic merge failed; fix conflicts and then commit the result.

В файле появятся маркеры:

function login() {
<<<<<<< HEAD
  return api.post('/auth/login');   // твой вариант (main)
=======
  return api.post('/auth/signin');  // вариант из ветки
>>>>>>> feature-login
}

Что делать:

  1. Открыть файл и вручную выбрать правильный вариант (или объединить оба).
  2. Удалить маркеры <<<<<<<, =======, >>>>>>>.
  3. Сохранить файл.
  4. Добавить его в индекс: git add src/login.js.
  5. Завершить merge: git commit.

Конфликт — не страшно. Это нормальная часть командной работы. Чем чаще мержишь ветки — тем меньше конфликтов.

Rebase — альтернатива merge

Rebase делает то же самое — переносит изменения из одной ветки в другую, — но по-другому. Вместо merge-коммита он «перебазирует» коммиты, создавая линейную историю.

# Находясь на feature-login
git rebase main

Что происходит:

До:
main:    A --- B --- E
                \
feature:         C --- D

После:
main:    A --- B --- E
                      \
feature:               C' --- D'

Коммиты C и D как бы «переиграны» поверх E. Получается линейная история без merge-коммита.

Merge vs rebase

КритерийMergeRebase
ИсторияСохраняет как былоПереписывает
Merge-коммитыСоздаётНе создаёт
ЧитаемостьВетвистаяЛинейная
БезопасностьВсегда безопасноОпасно на общих ветках
Золотое правило: не делай rebase на ветках, которые уже кто-то скачал. Rebase переписывает историю — у коллег всё сломается. На своих локальных ветках — можно.

Типичные сценарии

Обновить свою ветку до последнего main

# Переключаемся на main, обновляемся
git checkout main
git pull

# Возвращаемся в свою ветку
git checkout feature-login

# Вливаем в неё свежий main
git merge main
# или для чистой истории:
# git rebase main

Отменить незаконченный merge

git merge --abort

Взять один коммит из другой ветки

# Хеш коммита можно посмотреть через git log
git cherry-pick a1b2c3d

Что посмотреть

# История в виде графика со всеми ветками
git log --oneline --graph --all

# Что отличается в текущей ветке от main
git diff main..HEAD

# Список коммитов, которых нет в main
git log main..HEAD --oneline

Особенно полезен git log --oneline --graph --all — он рисует дерево коммитов в терминале. Сразу видно, где ветки разошлись и где слились.

Итог

Ветки — основа командной работы в Git. Создавай ветку под каждую фичу, работай в ней, потом сливай в main через merge или rebase. Конфликты — не страшно, их просто нужно решать руками. Главное правило: не делай rebase на чужих ветках.
