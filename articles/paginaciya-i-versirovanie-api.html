Пагинация и версионирование API — как не сломать клиентов

27 апреля 2026 • 11 мин чтения
Поделиться:

Представь: у тебя есть API, который отдаёт список статей. Сначала их было 10 — легко вернуть все разом. Потом стало 10 000. И тут начинается: клиент тормозит, сервер захлёбывается, а старые приложения ломаются от любого изменения. Разберём, как это решается.

Если ещё не читал про основы API — начни с той статьи.

Зачем пагинация

Отдать разом 10 000 записей — плохая идея:

  • Большой объём. Клиент получит мегабайты данных вместо нужных десяти.
  • Медленный запрос. База выполняет тяжёлый SELECT, сервер рендерит огромный JSON.
  • Плохой UX. Никто не читает все 10 000 записей сразу — пользователю нужна первая страница.

Пагинация разбивает список на страницы. Клиент запрашивает по одной.

Offset-пагинация — классика

Самый простой способ. Клиент указывает, сколько записей пропустить и сколько взять.

GET /api/articles?offset=0&limit=10      # первая десятка
GET /api/articles?offset=10&limit=10     # вторая десятка
GET /api/articles?offset=20&limit=10     # третья

Ответ — плюс метаданные:

{
  "items": [
    { "id": 1, "title": "Что такое API" },
    { "id": 2, "title": "Как работает DNS" }
  ],
  "total": 45,
  "offset": 0,
  "limit": 10,
  "next": "/api/articles?offset=10&limit=10"
}

Реализация на Python (SQLAlchemy):

def get_articles(offset=0, limit=10):
    total = session.query(Article).count()
    items = (
        session.query(Article)
        .order_by(Article.id)
        .offset(offset)
        .limit(limit)
        .all()
    )
    return {
        'items': [a.to_dict() for a in items],
        'total': total,
        'offset': offset,
        'limit': limit,
    }

Проблемы offset-пагинации

1. Медленно на больших offset. OFFSET 100000 заставляет базу отсчитать и выбросить 100 000 строк. Чем дальше — тем медленнее.

2. Сдвиг данных. Пока пользователь смотрит первую страницу, кто-то добавил новую запись. Пользователь открывает вторую — и видит одну и ту же запись дважды или пропускает другую.

Cursor-пагинация — современный подход

Вместо «пропусти N записей» клиент говорит «дай записи после вот этой». В качестве указателя (cursor) обычно используется ID или дата.

GET /api/articles?limit=10                    # первая страница
GET /api/articles?limit=10&after=42           # следующие после id=42
def get_articles(after=None, limit=10):
    query = session.query(Article).order_by(Article.id)

    if after:
        # Берём только записи с id больше after
        query = query.filter(Article.id > after)

    items = query.limit(limit).all()

    # Курсор для следующей страницы — id последней записи
    next_cursor = items[-1].id if items else None

    return {
        'items': [a.to_dict() for a in items],
        'next_cursor': next_cursor,
    }

Плюсы:

  • Быстро. База сразу идёт по индексу к нужному месту — не считает пропущенные.
  • Стабильно. Новые записи не сдвигают старые. Ничего не пропустишь и не увидишь дважды.

Минусы:

  • Нельзя прыгнуть на страницу 42. Только листать вперёд.
  • Нельзя отсортировать как угодно. Курсор привязан к конкретной сортировке.

Cursor-пагинация — стандарт для лент (Instagram, Twitter), чатов, логов. Offset — для админок с фильтрами и сортировками.

Версионирование API

Рано или поздно в API нужно что-то изменить. Но если изменить старый endpoint — все клиенты сломаются. Решение — версии.

Старые клиенты работают на v1, новые — на v2. Одновременно.

Способ 1. Версия в URL

Самый популярный вариант:

GET /api/v1/articles
GET /api/v2/articles

Плюсы:

  • Просто и понятно. Видно сразу в браузере.
  • Легко тестировать — меняешь v1 на v2 в URL.
  • Легко кэшировать — URL разные.

Минусы:

  • Ссылка «привязана» к версии — старые ссылки от старых клиентов работают всегда.
  • Нужно держать оба кода живыми.

Так делают Stripe, GitHub, Twilio. Это де-факто стандарт.

Способ 2. Версия в заголовке

GET /api/articles
Accept: application/vnd.myapi.v2+json

Плюсы: URL всегда один и тот же, «чистая» семантика.

Минусы: не видно в браузере, сложнее тестировать вручную, часть клиентов и прокси могут кэшировать неудачно.

Так делает GitHub в некоторых API. Для большинства проектов — избыточно.

Способ 3. Версия в параметре

GET /api/articles?version=2

Компромисс. Редко используется, но встречается у некоторых публичных API.

Что можно менять без версии

Не каждое изменение требует новой версии. Безопасные изменения:

  • Добавить новое необязательное поле в ответ. Старые клиенты его проигнорируют.
  • Добавить новый endpoint. Существующие клиенты его не используют.
  • Добавить необязательный параметр запроса. Старые запросы работают как раньше.

Опасные изменения — для них нужна новая версия:

  • Удалить поле из ответа. Старые клиенты могут его ожидать.
  • Переименовать поле. То же самое.
  • Изменить тип поля. Было число — стало строка.
  • Сделать необязательный параметр обязательным. Старые вызовы сломаются.
  • Поменять смысл поля. Клиент получит не то, что ожидал.
Правило: добавлять можно без версии, менять и удалять — только с новой версией.

Как поддерживать несколько версий

Внутри кода — три подхода.

1. Отдельные обработчики

from fastapi import FastAPI

app = FastAPI()

@app.get('/api/v1/articles')
def articles_v1():
    # Старый формат ответа
    return [{'id': 1, 'title': 'Статья', 'body': '...'}]

@app.get('/api/v2/articles')
def articles_v2():
    # Новый формат с тегами
    return [{
        'id': 1,
        'title': 'Статья',
        'content': '...',
        'tags': ['python', 'tutorial']
    }]

Просто, но код дублируется.

2. Один обработчик с трансформацией

@app.get('/api/{version}/articles')
def articles(version: str):
    items = fetch_articles()

    if version == 'v2':
        return [format_v2(item) for item in items]
    return [format_v1(item) for item in items]

Меньше дублей, но логика версий размазывается по коду.

3. Отдельные модули на версию

Самое чистое: папка api/v1/ и api/v2/. Каждая — со своими обработчиками. Общая бизнес-логика выносится в отдельный слой, который используют оба.

Когда удалять старую версию

Никогда — если нет веской причины. Клиенты могут быть не обновлены годами. Даже если у тебя «новое мобильное приложение», кто-то пользуется старой версией.

Если правда надо — предупреди за месяцы. Стандарты:

  • Заголовок Deprecation. Deprecation: true в ответе.
  • Sunset. Sunset: Sat, 01 Jan 2027 00:00:00 GMT — когда отключат.
  • Письмо разработчикам. За 3–6 месяцев до отключения.

Пример полного ответа API

{
  "items": [
    { "id": 42, "title": "Что такое API" },
    { "id": 43, "title": "Как работает DNS" }
  ],
  "pagination": {
    "limit": 10,
    "next_cursor": 43,
    "has_more": true
  },
  "meta": {
    "version": "v2",
    "generated_at": "2026-04-27T12:00:00Z"
  }
}

Тут три уровня: данные, пагинация, метаинформация. Такой ответ и стабильный, и информативный.

Итог

Пагинация обязательна, если данных больше сотни. Offset прост, но медленный на глубине и сдвигается при изменениях. Cursor быстрый и стабильный — стандарт для лент. Версии в URL — самый частый и удобный способ версионировать API. Добавлять можно без версии, менять и удалять — только с новой. Старую версию не удаляй, пока клиенты не отвалятся сами.
