Модульные тесты: зачем они нужны и как их писать

17 марта 2026 • 10 мин чтения
Поделиться:

Начинающий программист пишет функцию, запускает — работает. Через месяц что-то правит — функция ломается, но узнаёт об этом только когда пользователь жалуется. Модульные тесты решают эту проблему: код сам себя проверяет.

Что такое модульный тест

Это маленькая программа, которая проверяет одну функцию. Ты пишешь: «функция сложения двух чисел с аргументами 2 и 3 должна вернуть 5». Запускаешь тест — он либо проходит, либо падает. Всё.

Если ты что-то поменял в коде и сломал эту функцию — тест сразу скажет об этом. Не через месяц на проде, а через 2 секунды после сохранения.

Зачем это нужно

  • Ловишь баги мгновенно. Сломал — узнал сразу.
  • Уверенно рефакторишь. Меняешь внутренности, запускаешь тесты — если зелёные, всё ок.
  • Документирует код. Читая тест, видно, что функция должна делать.
  • Без тестов в профессию не берут. На собеседованиях спрашивают, на работе требуют.

Первый тест на JavaScript

Самый популярный инструмент — Jest. Пишем функцию и её тест:

// math.js — тестируемая функция
function add(a, b) {
  return a + b;
}

module.exports = { add };

// math.test.js — тест
const { add } = require('./math');

test('2 + 3 = 5', () => {
  expect(add(2, 3)).toBe(5);
});

test('работает с отрицательными', () => {
  expect(add(-2, -3)).toBe(-5);
});

test('работает с нулём', () => {
  expect(add(0, 7)).toBe(7);
});

Что тут происходит:

  • test('название', ...) — объявляет один тест с понятным названием.
  • expect(значение).toBe(ожидаемое) — проверка. Если не совпало — тест падает с ошибкой.
  • Таких тестов пишут несколько — на разные случаи.

Что тестировать в первую очередь

  1. Чистые функции. Те, которые принимают данные и возвращают результат — без побочек. Тестировать легко.
  2. Граничные случаи. Ноль, отрицательные числа, пустая строка, очень большое число.
  3. Ошибки. Что функция делает, если пришло не то, что ожидалось.
  4. Основную логику бизнеса. Расчёт цены со скидкой, проверка пароля и т.п.

Что НЕ надо тестировать

  • Чужой код. Не пиши тесты на библиотеки — их уже протестировали авторы.
  • Простые геттеры и сеттеры. getName() { return this.name; } — тут нечего проверять.
  • Всё подряд. Не надо 100% покрытия. 70-80% — хороший уровень, 100% часто бессмысленно.

Главные принципы

Один тест = одна проверка. Название теста описывает, что проверяем — и оно должно быть понятно через год.
  • AAA-структура. Arrange (подготовь), Act (выполни), Assert (проверь).
  • Тест не должен зависеть от других тестов. Каждый работает сам по себе.
  • Тесты запускаются быстро. Секунды, не минуты. Иначе ты их перестанешь запускать.

Что важно запомнить

  • Тест — маленькая программа, которая проверяет функцию.
  • Пишутся до или вместе с кодом, не после.
  • Главный фреймворк в JS — Jest, в Python — pytest.
  • expect(результат).toBe(ожидаемое) — база для проверок.
  • Не гонись за 100% покрытием. 70% — уже отлично.
  • Без тестов код работает только «пока никто не трогал».
