Что такое кэширование и зачем оно нужно

2 апреля 2026 • 10 мин чтения
Поделиться:

Кэширование — одна из тех идей, которая кажется простой, пока не начнёшь делать это в реальном проекте. Здесь легко и ускорить систему в 100 раз, и положить её полностью. Разберёмся.

Зачем вообще кэш

Задача проста: если данные уже считались один раз, зачем считать их снова?

Пример: главная страница сайта показывает топ-10 популярных статей. Эта информация обновляется раз в сутки. Логично: посчитать один раз и сохранить результат, вместо того чтобы дёргать базу на каждый запрос от каждого пользователя.

Кэш — это компромисс: жертвуем актуальностью ради скорости.

Уровни кэширования

Кэш бывает на каждом уровне системы. Вот по порядку — от пользователя до базы данных.

1. Браузерный кэш

Браузер сохраняет CSS, JS, картинки и не запрашивает их заново при повторном открытии сайта. Управляется HTTP-заголовками:

Cache-Control: max-age=86400
ETag: "abc123"

max-age=86400 значит: держи в кэше 24 часа. ETag — это версия файла, чтобы проверить, изменился ли он.

2. CDN-кэш

CDN (Content Delivery Network) — сеть серверов по всему миру. Она хранит копии статики (картинки, видео, JS) ближе к пользователю. Пользователь из Новосибирска получает картинку с сервера в Новосибирске, а не с сервера в США.

Cloudflare, Fastly, CloudFront — популярные CDN.

3. Кэш приложения

Самый хитрый уровень. Внутри твоего бэкенда можно кэшировать результаты тяжёлых вычислений, ответы внешних API, готовые HTML-страницы.

Способы:

  • In-memory — прямо в переменных процесса.
  • Redis / Memcached — отдельный сервер, кэш общий для всех инстансов приложения.
  • Локальный файл — для простых случаев.

4. Кэш базы данных

Современные СУБД сами кэшируют часто используемые данные в памяти. Postgres, MySQL, MongoDB — у всех есть внутренние буферы.

Часто этого достаточно, и дополнительный кэш на уровне приложения не нужен. Прежде чем тащить Redis, проверь, не решит ли вопрос индекс или правильный запрос.

Что кэшировать: паттерны

Два самых популярных паттерна использования кэша.

Cache-aside (lazy loading)

Приложение само решает, что кэшировать. Алгоритм:

  1. Проверяем данные в кэше.
  2. Если есть — отдаём (попадание, cache hit).
  3. Если нет — идём в источник, сохраняем в кэш, отдаём (промах, cache miss).
def get_user(user_id):
    cached = redis.get(f'user:{user_id}')
    if cached:
        return json.loads(cached)
    user = db.query('SELECT * FROM users WHERE id = ?', user_id)
    redis.setex(f'user:{user_id}', 3600, json.dumps(user))
    return user

Плюс: кэшируется только то, что реально запрашивают. Минус: первый запрос всегда медленный.

Write-through

При записи данных в базу одновременно пишем и в кэш. Данные всегда актуальны, но пишем чаще.

Используется, когда данные часто читают сразу после записи.

Что такое TTL

TTL (Time To Live) — время жизни записи в кэше. Через TTL данные автоматически удаляются, и при следующем запросе подтягиваются свежие.

Выбор TTL — компромисс:

  • Долгий TTL — меньше нагрузки, но данные могут быть устаревшими.
  • Короткий TTL — актуально, но нагрузка возвращается.

Ориентиры:

ДанныеРазумный TTL
Курсы валют5–15 минут
Топ статей на главной1 час
Профиль пользователя5–30 минут
Настройки приложенияСутки
Справочник странДни или недели

Инвалидация — самая сложная часть

Инвалидация — это удаление или обновление устаревших записей в кэше. Звучит просто, но на практике именно тут всё ломается.

Пример проблемы: пользователь сменил имя. Ты обновил запись в базе, но в кэше старые данные. Сайт показывает старое имя час — пока не истечёт TTL.

Варианты решения:

  • TTL. Рано или поздно кэш сам обновится. Работает, если небольшая задержка допустима.
  • Ручное удаление. После обновления данных в базе — удалить ключ из кэша.
  • Версионирование ключей. Вместо user:42 использовать user:42:v5. Смена версии — все старые ключи «протухают».
В программировании две сложные вещи: инвалидация кэша, придумывание имён и ошибки на единицу. — шутка, но с долей правды.

Проблема «пробоя кэша» (cache stampede)

Ещё одна классическая проблема. Популярный ключ с TTL истекает, и в этот момент сотни запросов одновременно идут в базу, чтобы его пересчитать. База падает.

Решения:

  • Локи. Только один процесс обновляет значение, остальные ждут.
  • Early refresh. Обновлять кэш заранее, до истечения TTL.
  • Джиттер. Не давать всем ключам истекать в одну секунду — добавлять случайную задержку.

Что НЕ надо кэшировать

  • Персональные данные без разбора — можно случайно отдать чужому пользователю.
  • Пароли и токены в открытом виде — утечка.
  • Данные, которые обновляются чаще, чем читаются — кэш только мешает.
  • Результаты, чувствительные ко времени — если данные устаревают за секунду, кэш бессмысленен.

Инструменты

ИнструментОсобенность
RedisСамый популярный. Много структур данных, персистентность.
MemcachedПроще и быстрее, но только key-value.
VarnishКэш для HTTP на уровне прокси.
Nginx proxy_cacheПростой HTTP-кэш на уровне веб-сервера.

Итог

Кэширование — один из самых мощных инструментов ускорения. Оно есть на всех уровнях: браузер, CDN, приложение, база. Главное — правильно выбрать TTL и стратегию инвалидации, чтобы не отдавать пользователям устаревшее. И помнить: кэш — не бесплатный — он добавляет сложности, за которые нужно платить вниманием.
