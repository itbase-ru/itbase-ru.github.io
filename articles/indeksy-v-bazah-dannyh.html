Индексы в базах данных — зачем и как работают

9 апреля 2026 • 11 мин чтения
Поделиться:

Если ты когда-нибудь ждал ответа от сайта 10 секунд, а потом открывал тот же раздел мгновенно — скорее всего, дело было в индексах. Разберёмся, что это и почему без них база данных работает в разы медленнее.

Если ещё не читал про SQL-запросы — начни с той статьи.

Проблема, которую решают индексы

Представь таблицу users с миллионом строк. Ты пишешь:

SELECT * FROM users WHERE email = 'kirill@mail.ru';

Без индекса база данных читает каждую строку одну за другой, пока не найдёт нужную. Это называется full table scan. На миллионе строк — это секунды.

С индексом — миллисекунды. Потому что база сразу знает, где искать.

Индекс — это как алфавитный указатель в конце книги. Вместо того чтобы листать всю книгу в поиске нужного слова, ты открываешь указатель и сразу видишь номер страницы.

Как устроен индекс

Самый распространённый тип — B-tree (сбалансированное дерево). Внутри — отсортированная структура, где каждый узел содержит диапазон значений.

Схематично для поля email:

                [m@mail.ru]
              /             \
      [a...m]                [n...z]
     /       \              /       \
  [a...f]  [g...m]      [n...s]   [t...z]

Поиск идёт от корня вниз — на каждом уровне отсекается половина вариантов. На миллионе записей нужно всего около 20 сравнений. Отсюда скорость.

Создание индекса

-- Простой индекс по одному полю
CREATE INDEX idx_users_email ON users (email);

-- Уникальный индекс — гарантирует уникальность значений
CREATE UNIQUE INDEX idx_users_email_unique ON users (email);

-- Удалить индекс
DROP INDEX idx_users_email;

После создания индекс начинает использоваться автоматически. Писать запросы по-другому не нужно.

Когда индекс помогает

Индекс ускоряет:

  • WHERE — фильтрация по индексированному полю.
  • JOIN — соединение таблиц по индексированному полю.
  • ORDER BY — сортировка, если индекс уже упорядочен.
  • GROUP BY — группировка по индексированному полю.

Пример:

-- До индекса: 2 секунды (полный перебор миллиона строк)
-- После индекса: 5 миллисекунд
SELECT * FROM orders WHERE user_id = 42;

Когда индекс не помогает

Индекс работает плохо или вообще игнорируется, если:

  • Условие с функцией от поля. WHERE LOWER(email) = 'x' — индекс по email не сработает. Нужен функциональный индекс: CREATE INDEX ON users (LOWER(email)).
  • Поиск по подстроке в середине. WHERE email LIKE '%mail%' — индекс не поможет, потому что неизвестно, с чего начинать поиск. А вот LIKE 'kirill%' — работает.
  • Низкая селективность. Если поле имеет 2–3 значения (например, пол), индекс почти не помогает — база всё равно прочитает половину таблицы.
  • Отрицание в WHERE. WHERE status != 'done' — часто игнорирует индекс.

Составные индексы

Можно индексировать сразу несколько полей. Это полезно, если ты часто фильтруешь по комбинации:

-- Индекс по двум полям
CREATE INDEX idx_orders_user_status ON orders (user_id, status);

-- Такой индекс ускорит:
SELECT * FROM orders WHERE user_id = 42 AND status = 'paid';
SELECT * FROM orders WHERE user_id = 42;

-- Но не ускорит:
SELECT * FROM orders WHERE status = 'paid';

Правило левого префикса: составной индекс работает, если запрос использует левое начало списка полей. В примере выше — user_id идёт первым, поэтому запросы только по user_id тоже работают. А только по status — нет.

Порядок полей в составном индексе

Обычно первым ставят поле с наибольшей селективностью — то, что сильнее всего отсекает строки.

Пример: orders с полями user_id (много разных значений) и status (всего 3–4 значения).

Лучше (user_id, status), а не (status, user_id). Потому что user_id отсекает больше, а status уже добивает остаток.

Покрывающий индекс

Особый вид: индекс содержит все поля, которые нужны запросу. Тогда база данных вообще не обращается к самой таблице — берёт всё из индекса. Это очень быстро.

-- Запрос нуждается в двух полях
SELECT user_id, status FROM orders WHERE user_id = 42;

-- Покрывающий индекс
CREATE INDEX idx_orders_user_status ON orders (user_id, status);
-- Всё нужное лежит в индексе — таблица не читается

Цена индексов

Индексы — не бесплатные. Они:

  • Занимают место на диске — иногда столько же, сколько сама таблица.
  • Замедляют INSERT, UPDATE, DELETE — потому что при изменении данных индекс тоже нужно обновить.
  • Требуют времени на создание — на больших таблицах это часы.
Индекс — это компромисс: читаем быстрее, пишем медленнее. Если таблица в основном пишется (логи, события), много индексов — плохая идея.

Как проверить, используется ли индекс

Есть специальная команда EXPLAIN — она показывает план выполнения запроса:

EXPLAIN SELECT * FROM users WHERE email = 'kirill@mail.ru';

В выводе смотри на:

  • Seq Scan (или Full Table Scan) — плохо, индекс не используется.
  • Index Scan — хорошо, индекс работает.
  • Index Only Scan — идеально, покрывающий индекс.

На EXPLAIN ANALYZE (с анализом) покажет ещё и реальное время выполнения:

EXPLAIN ANALYZE SELECT * FROM users WHERE email = 'kirill@mail.ru';

Практические советы

  1. Индексируй внешние ключи. user_id, order_id — их всегда используют в JOIN.
  2. Индексируй поля в WHERE и ORDER BY. Если по полю часто фильтруешь — индексируй.
  3. Не индексируй всё подряд. Каждый индекс замедляет запись.
  4. Проверяй EXPLAIN. После создания индекса убедись, что запрос его реально использует.
  5. Начинай с простого. Не делай сразу десять индексов — начни с тех, что нужны самому частому запросу.

Типы индексов в PostgreSQL

ТипДля чего
B-treeСтандартный. Для =, <, >, ORDER BY, LIKE с префиксом
HashТолько для =. Редко используется
GINДля полнотекстового поиска, массивов, JSONB
GiSTДля геометрии, диапазонов
BRINДля больших таблиц с упорядоченными данными (логи, метрики)

Для 95% случаев B-tree — то, что нужно. Остальные — нишевые.

Итог

Индексы — главный инструмент ускорения запросов. Работают через структуру типа дерева, отсекая половину вариантов на каждом шаге. Замедляют запись, но в разы ускоряют чтение. Составные индексы — под конкретные запросы, покрывающие — самый быстрый вариант. Проверяй всё через EXPLAIN.
