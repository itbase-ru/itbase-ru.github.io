REST и GraphQL — в чём разница

30 марта 2026 • 10 мин чтения
Поделиться:

Если ты пишешь или потребляешь API — рано или поздно встанет вопрос: REST или GraphQL? Оба подхода живые, оба популярные. Разбираем, чем они отличаются и когда что выбирать.

Если ты ещё не читал основы про API — начни с той статьи, там база.

REST — что это

REST (Representational State Transfer) — архитектурный стиль, построенный на ресурсах и HTTP-методах. Ты обращаешься к URL, а метод говорит, что делать:

  • GET — получить данные.
  • POST — создать новое.
  • PUT / PATCH — обновить существующее.
  • DELETE — удалить.

Пример: интернет-магазин.

GET    /users/42          → данные пользователя
GET    /users/42/orders   → его заказы
POST   /orders            → создать заказ
PATCH  /orders/17         → изменить заказ
DELETE /orders/17         → удалить заказ

REST прост, предсказуем и «родной» для HTTP. За это его любят уже 20 лет.

Проблемы REST

У REST есть два классических болевых места.

1. Over-fetching — данных больше, чем нужно

Клиенту нужно только имя и аватар пользователя. А GET /users/42 отдаёт всё: адрес, телефон, дату рождения, настройки. Ты тянешь лишнее и тратишь трафик.

2. Under-fetching — данных меньше, чем нужно

Нужны данные пользователя и его последние заказы и отзывы. Приходится делать три запроса:

GET /users/42
GET /users/42/orders?limit=10
GET /users/42/reviews?limit=5

На мобильном интернете это ощутимо. Плюс каждый запрос — отдельный round-trip к серверу.

GraphQL — что это

GraphQL придумали в Facebook в 2012 (открыли в 2015). Идея: один endpoint, а клиент сам описывает, какие данные ему нужны.

Запрос на GraphQL — это не URL, а специальный язык:

{
  user(id: 42) {
    name
    avatar
    orders(last: 10) {
      id
      total
      status
    }
  }
}

Тот же запрос, что выше делал 3 вызова REST, здесь — один. И приходит ровно то, что запрошено: ничего лишнего.

Когда REST лучше

  • Простые CRUD-приложения. Блог, задача-менеджер, админка — REST хватит с головой.
  • Публичное API для внешних разработчиков. REST-стиль понятен почти всем, документация простая.
  • Кэширование критично. HTTP-кэш, CDN, ETag — всё работает с REST «бесплатно».
  • Загрузка файлов. Multipart в REST — стандарт, в GraphQL — отдельная история.
  • Маленькая команда. Меньше сложности — меньше шансов запутаться.

Когда GraphQL лучше

  • Мобильные приложения с медленной сетью. Один запрос вместо трёх — большая экономия.
  • Сложные клиенты с разными потребностями. Веб-версия хочет одно, мобильная — другое, GraphQL отдаёт каждой нужное.
  • Много связанных сущностей. Соцсеть, маркетплейс, дашборд со связями — GraphQL удобнее.
  • Быстрая итерация на фронте. Новое поле — без изменения бэкенда и без новых endpoint'ов.
  • Типизация важна. Схема GraphQL сама является документацией.

Что такое «N+1 проблема» в GraphQL

Тут GraphQL не так прост, как кажется. Если написать наивно, один запрос GraphQL может превратиться в сотню запросов к базе данных. Например, ты запросил 10 заказов, и для каждого надо подтянуть данные пользователя — выходит 11 SQL-запросов вместо двух.

Решается через DataLoader — специальный механизм batching'а и кэширования. Но это уже ответственность бэкенд-разработчика.

Что выбрать на практике

Если ты делаешь небольшое приложение или изучаешь веб — начинай с REST. Проще, понятнее, больше примеров.

Если у тебя сложный фронтенд с множеством компонентов, каждый из которых дёргает свой кусок данных, — присмотрись к GraphQL.

Реальность такова: большинство команд спокойно живут на REST. GraphQL выигрывает, когда REST начинает болеть — то есть когда клиентов много, а данные связаны.

А есть ещё tRPC, gRPC и другие

За кадром этой статьи остались:

  • gRPC — бинарный протокол Google для микросервисов, быстрый, но не для браузера «из коробки».
  • tRPC — TypeScript-фреймворк для full-stack проектов, даёт end-to-end типизацию.
  • WebSocket — для real-time, это вообще не про REST или GraphQL.

Но это темы для отдельных статей.

Итог

REST — проверенный, простой, хорошо кэшируется. GraphQL — гибкий, экономит запросы, но требует больше инфраструктуры. Не гонись за модой: выбирай инструмент под задачу.
