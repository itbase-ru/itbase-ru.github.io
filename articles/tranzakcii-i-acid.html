Транзакции в базах данных — ACID простыми словами

21 апреля 2026 • 11 мин чтения
Поделиться:

Представь перевод денег с карты на карту. С твоего счёта списалось 1000 рублей, но у получателя они не появились из-за сбоя. Деньги исчезли. Именно от такого защищают транзакции.

Если ещё не читал про SQL-запросы — начни с той статьи.

Что такое транзакция

Транзакция — это группа операций, которая выполняется целиком или не выполняется вообще. Промежуточного состояния быть не может.

Пример перевода денег — это две операции:

  1. Списать 1000 с одного счёта.
  2. Зачислить 1000 на другой.

Если первая прошла, а вторая упала — деньги потеряны. Транзакция гарантирует: либо обе прошли, либо ни одна.

Транзакция — как кнопка «Сохранить» в документе: либо всё, либо ничего.

Пример на SQL

-- Начинаем транзакцию
BEGIN;

-- Списываем со счёта отправителя
UPDATE accounts
SET balance = balance - 1000
WHERE id = 1;

-- Зачисляем получателю
UPDATE accounts
SET balance = balance + 1000
WHERE id = 2;

-- Подтверждаем — обе операции сохраняются вместе
COMMIT;

Если между UPDATE что-то падает — мы вызываем ROLLBACK и обе операции отменяются:

BEGIN;

UPDATE accounts SET balance = balance - 1000 WHERE id = 1;

-- Что-то пошло не так → откатываем всё
ROLLBACK;

После ROLLBACK база вернётся в состояние, как будто транзакции вообще не было.

Четыре свойства — ACID

Это аббревиатура из четырёх английских слов. Каждое описывает одну гарантию транзакции.

A — Atomicity (атомарность)

Все операции внутри транзакции — единое целое. Либо все выполнятся, либо ни одна. Не бывает так, что «списание прошло, а зачисление — нет».

C — Consistency (согласованность)

После транзакции база остаётся в корректном состоянии. Все правила и ограничения соблюдены. Например, если у тебя правило «баланс не может быть отрицательным», транзакция не пройдёт, если она нарушит это правило.

I — Isolation (изоляция)

Параллельные транзакции не видят друг друга «изнутри». Пока ты не завершил транзакцию, другие пользователи видят базу в прежнем состоянии.

Это самое сложное свойство. Об изоляции — отдельно ниже.

D — Durability (надёжность)

После COMMIT данные сохранены навсегда. Даже если сервер выключится, свет пропадёт или диск сломается — после перезапуска данные на месте.

Достигается через журналирование: все изменения сначала пишутся в лог, потом применяются к базе.

Проблемы параллельности

Когда две транзакции работают одновременно, возникают классические проблемы.

Грязное чтение (dirty read)

Одна транзакция читает данные, которые другая ещё не подтвердила. Если вторая откатится — первая работала с «фантомом».

Неповторяющееся чтение

Транзакция дважды читает одну строку и получает разные данные — потому что между чтениями вторая транзакция её изменила.

Фантомное чтение

Транзакция дважды выполняет один запрос и получает разное количество строк — потому что вторая транзакция добавила или удалила записи.

Уровни изоляции

Полная изоляция замедляет базу. Поэтому есть четыре уровня — от самого быстрого и небезопасного до самого строгого и медленного.

УровеньГрязное чтениеНеповторяющеесяФантомное
Read uncommittedВозможноВозможноВозможно
Read committedНетВозможноВозможно
Repeatable readНетНетВозможно
SerializableНетНетНет

Как выбрать:

  • Read committed — дефолт в PostgreSQL. Достаточно для большинства задач.
  • Repeatable read — когда важно видеть стабильные данные в рамках транзакции.
  • Serializable — для критичных расчётов, где важна абсолютная точность.

Чем выше уровень — тем больше блокировок и тем медленнее база.

Пример проблемы на практике

Два человека одновременно покупают последний товар на складе (осталось 1 штука).

-- Транзакция 1
BEGIN;
SELECT quantity FROM products WHERE id = 42;   -- видит 1
-- ... думает ...

-- Транзакция 2 (в тот же момент)
BEGIN;
SELECT quantity FROM products WHERE id = 42;   -- тоже видит 1
-- ... тоже думает ...

-- Обе решают: товар есть, можно продавать
-- Обе делают:
UPDATE products SET quantity = quantity - 1 WHERE id = 42;

-- Итог: продали два товара, хотя был один
COMMIT;

Это называется гонка. Решается через блокировки или правильный уровень изоляции.

Решение — блокировка строки

BEGIN;

-- Блокируем строку, пока не закончим транзакцию
SELECT quantity FROM products WHERE id = 42 FOR UPDATE;

-- Вторая транзакция будет ждать, пока первая не завершится
UPDATE products SET quantity = quantity - 1 WHERE id = 42;

COMMIT;

FOR UPDATE блокирует строку. Вторая транзакция подождёт, потом увидит quantity = 0 и откажет покупателю.

Блокировки и дедлоки

Блокировки защищают от гонок, но создают новые проблемы. Если две транзакции заблокируют разные строки и потом попробуют заблокировать строки друг друга — возникает дедлок (взаимная блокировка).

Пример:

  • Транзакция A блокирует строку 1, хочет строку 2.
  • Транзакция B блокирует строку 2, хочет строку 1.
  • Обе ждут вечно.

СУБД сама разрешает дедлок: одну из транзакций она принудительно откатит. Важно быть готовым к тому, что транзакция может откатиться — и обработать это в коде.

В коде приложения

Python + SQLAlchemy:

from sqlalchemy.orm import Session

def transfer_money(session, from_id, to_id, amount):
    try:
        # Списываем
        from_account = session.query(Account).get(from_id)
        from_account.balance -= amount

        # Зачисляем
        to_account = session.query(Account).get(to_id)
        to_account.balance += amount

        # Фиксируем — обе операции вместе
        session.commit()
    except Exception as error:
        # Что-то упало — откатываем всё
        session.rollback()
        raise error

Здесь commit() = COMMIT в SQL. rollback() = ROLLBACK.

Когда транзакции не нужны

  • Чтение данных без изменений. Просто SELECT — транзакция не нужна.
  • Одиночная вставка. Если это один INSERT без зависимостей — можно без BEGIN/COMMIT.
  • Логирование и метрики. Тут наоборот — потеря одной записи не критична.

Частые ошибки

  • Долгие транзакции. Открыл BEGIN, сходил на обед, вернулся — транзакция всё ещё держит блокировки. Другие ждут. Транзакции должны быть короткими.
  • Транзакции в цикле. Не открывай отдельную транзакцию для каждой итерации — это медленно.
  • Забыть commit. Данные не сохранятся. Или откатятся при разрыве соединения.
  • Ловить все исключения. Если ловишь except Exception — не забудь сделать rollback, иначе сессия останется в нерабочем состоянии.

Итог

Транзакция — группа операций, которая выполняется целиком или не выполняется вообще. Четыре свойства ACID: атомарность, согласованность, изоляция, надёжность. Уровни изоляции балансируют между точностью и скоростью. Для критичных операций — блокировки через FOR UPDATE. Не забывай про rollback при ошибках и держи транзакции короткими.
