Что такое DevOps — CI/CD и деплой простыми словами

25 марта 2026 • 10 мин чтения
Поделиться:

«DevOps», «CI/CD», «пайплайн», «деплой» — это слова из вакансий, тимлидов на планёрках и статей на Хабре. Разберём их по-человечески: что это, зачем и как выглядит на практике.

Что такое DevOps

DevOps — это не инструмент и не должность. Это культура и подход, при котором разработка (Dev) и эксплуатация (Ops) работают вместе, а не через стену.

Раньше было так: разработчики пишут код и «кидают через забор» админам, чтобы те развернули. Админы разворачивают, что-то падает, начинается переписка «это ваш код» — «нет, это ваша инфраструктура». Виноватых нет, продукт страдает.

DevOps — это когда человек, написавший код, отвечает за то, как этот код работает в проде. А тот, кто держит инфраструктуру, помогает ему это делать быстро и безопасно.

Из чего состоит DevOps

Три кита, на которых всё держится:

  1. CI — Continuous Integration (непрерывная интеграция).
  2. CD — Continuous Delivery / Deployment (непрерывная доставка или развёртывание).
  3. Infrastructure as Code (инфраструктура как код) — про это отдельно, но упомянем.

CI — непрерывная интеграция

Раньше разработчики могли неделями писать код в своих ветках, а потом «в пятницу вечером» сливать всё в основную. И всё ломалось — конфликты, ошибки, «а у меня локально работало».

CI решает это просто: каждое изменение автоматически собирается и тестируется. Запушил код — через пять минут знаешь, что что-то пошло не так.

Что обычно делает CI:

  • запускает линтеры и проверку стиля;
  • прогоняет unit-тесты;
  • собирает проект (если это компилируемый язык);
  • запускает интеграционные тесты;
  • сообщает результат в PR.

Если CI красный — PR не мержится. Простое правило, которое спасает проекты.

CD — непрерывная доставка и развёртывание

Тут есть путаница из-за одинаковой аббревиатуры. Различай:

ТерминЧто делаетЧто решает человек
Continuous DeliveryГотовит релиз, но не выкатываетКогда нажать «выкатить»
Continuous DeploymentВыкатывает автоматическиНичего, всё само

Continuous Delivery — это когда после каждого успешного CI собирается готовый к релизу артефакт. Осталось нажать кнопку. Continuous Deployment идёт дальше — вообще без кнопки: прошли тесты, значит в прод.

Второй вариант страшнее для новичка, но именно к нему стремятся зрелые команды. Главное — иметь быстрый откат, если что-то пошло не так.

Как это выглядит на практике

Всё вместе называется pipeline — конвейер. Схематично:

git push → lint → test → build → deploy to staging → deploy to prod

Каждый шаг — это скрипт, который запускается автоматически. Если на любом шаге падает — следующие не запускаются, приходит уведомление.

Пример простого CI-конфига для GitHub Actions (.github/workflows/ci.yml):

name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
      - run: npm ci
      - run: npm test

Читается буквально: «на каждый пуш и PR в main запусти на Ubuntu: скачай код, поставь Node 20, установи зависимости, прогони тесты».

Что такое деплой

Деплой (deploy) — это выкладка готовой версии приложения туда, где ей пользуются люди. Может быть:

  • Прод — сервер, куда ходят реальные пользователи.
  • Staging — копия прода, чтобы проверить перед выкаткой.
  • Dev — среда для разработки.

Способы деплоя различаются:

  1. Простой. Остановили сервер, залили новую версию, включили. Есть простой — пользователи видят ошибку.
  2. Blue-green. Есть две среды: blue (текущая) и green (новая). Переключаем трафик на green — если всё ок, blue становится новой green.
  3. Canary. Сначала отправляем 5% трафика на новую версию. Если метрики в норме — катим дальше.
  4. Rolling. Обновляем серверы по одному, не выключая весь сервис.

Чем больше нагрузка и чем критичнее сервис, тем хитрее схема деплоя.

DevOps для одного человека

DevOps-подход полезен даже если ты один делаешь пет-проект:

  • GitHub Actions запускает тесты на каждый PR — десять минут настройки, экономит часы.
  • Docker упаковывает приложение — «работает у меня, работает у всех».
  • Автоматический деплой из main-ветки — не нужно руками заливать файлы по FTP.
  • Мониторинг — хотя бы простой аптайм-чек через UptimeRobot.
DevOps — это не «админ, который умеет в Docker». Это способ убрать трение между «я написал код» и «люди этим пользуются».
