Docker Compose — несколько контейнеров одной командой

18 апреля 2026 • 10 мин чтения
Поделиться:

Один контейнер — просто. А если у тебя бэкенд на Python, база PostgreSQL, кэш в Redis и фоновый воркер? Запускать четыре контейнера руками каждый раз — мучение. Docker Compose решает это одним файлом.

Если ещё не читал основы Docker — начни со статьи Docker за 10 минут.

Что такое Docker Compose

Docker Compose — инструмент, который позволяет описать несколько контейнеров в одном файле и управлять ими вместе. Одна команда — и всё приложение поднимается со всеми зависимостями.

Без Compose нужно было бы:

docker run -d postgres
docker run -d redis
docker run -d --link postgres --link redis my-backend
# И каждый раз помнить все параметры

С Compose:

docker compose up

Одна строка. Все контейнеры собираются, запускаются и связываются между собой.

Файл docker-compose.yml

Описывается всё в одном файле в корне проекта. Формат — YAML.

# Версия формата (в новых версиях Docker можно не указывать)
version: '3.9'

services:
  # Приложение на Python
  backend:
    build: .                       # собрать из Dockerfile в текущей папке
    ports:
      - "8000:8000"                # пробросить порт 8000 наружу
    environment:                   # переменные окружения
      - DATABASE_URL=postgresql://user:pass@db:5432/app
      - REDIS_URL=redis://cache:6379
    depends_on:                    # порядок запуска
      - db
      - cache
    volumes:
      - ./src:/app/src             # локальная папка внутрь контейнера

  # База данных
  db:
    image: postgres:16             # готовый образ из Docker Hub
    environment:
      - POSTGRES_USER=user
      - POSTGRES_PASSWORD=pass
      - POSTGRES_DB=app
    volumes:
      - pgdata:/var/lib/postgresql/data   # сохранить данные

  # Кэш
  cache:
    image: redis:7-alpine

# Именованные тома — данные переживают перезапуск
volumes:
  pgdata:

Разберём по частям.

services — основные блоки

Каждый service — это один контейнер. У него есть имя (в примере: backend, db, cache), которое автоматически становится сетевым адресом.

Внутри бэкенда можно обращаться к базе по имени сервиса:

postgresql://user:pass@db:5432/app
#                    ↑↑
#                    имя сервиса, а не localhost

Docker поднимает внутреннюю сеть, в которой все сервисы видят друг друга по именам.

build — из своего Dockerfile

Для приложения, у которого есть свой код, используется build:

backend:
  build: .              # в корне, где Dockerfile
  # или указать путь
  build: ./backend
  # или расширенная настройка
  build:
    context: .
    dockerfile: Dockerfile.prod

image — готовый образ

Для готовых сервисов — Postgres, Redis, Nginx — используется image:

db:
  image: postgres:16     # официальный образ, версия 16
  image: redis:7-alpine  # Redis 7 на Alpine (маленький образ)

ports — доступ снаружи

ports:
  - "8000:8000"    # хост:контейнер
  - "5432:5432"    # откроем базу наружу для отладки
  - "80:80"        # веб-сервер

Важно: для базы данных наружу порт обычно не открывают — это опасно. Оставляй базу доступной только внутри Docker-сети. Для локальной отладки можно открыть, но не на проде.

environment — переменные окружения

Три способа задать переменные:

# 1. Список
environment:
  - DATABASE_URL=postgresql://user:pass@db:5432/app

# 2. Словарь (эквивалент)
environment:
  DATABASE_URL: postgresql://user:pass@db:5432/app

# 3. Из файла .env — самый правильный путь
env_file:
  - .env

Пароли и ключи лучше держать в .env — и обязательно добавить его в .gitignore, чтобы не улетел в GitHub.

volumes — постоянное хранилище

Контейнеры легко удаляются и создаются заново. Но данные в базе должны оставаться. Для этого есть тома.

db:
  volumes:
    # именованный том — Docker сам управляет
    - pgdata:/var/lib/postgresql/data

    # прямой маппинг папки с хоста — для разработки
    - ./migrations:/docker-entrypoint-initdb.d

Два вида:

  • Именованные тома (pgdata:/path) — живут на хосте, переживают перезапуск. Данные базы.
  • Bind mounts (./src:/app/src) — прямая связь с локальной папкой. Изменения в коде сразу видны в контейнере. Для разработки.

depends_on — порядок запуска

backend:
  depends_on:
    - db
    - cache

Docker запустит db и cache первыми. Но не ждёт их полной готовности — только старта контейнера. Если твоё приложение сразу дёргает базу, а Postgres ещё не готов, оно упадёт.

Решение — healthcheck:

db:
  image: postgres:16
  healthcheck:
    test: ["CMD-SHELL", "pg_isready -U user"]
    interval: 5s
    timeout: 5s
    retries: 5

backend:
  depends_on:
    db:
      condition: service_healthy   # ждать готовности базы

Основные команды

КомандаЧто делает
docker compose upЗапустить всё
docker compose up -dЗапустить в фоне
docker compose up --buildПересобрать образы и запустить
docker compose downОстановить и удалить контейнеры
docker compose down -vТо же + удалить тома (данные)
docker compose psСписок запущенных
docker compose logs -f backendЛоги сервиса в реальном времени
docker compose exec backend bashЗайти внутрь контейнера
docker compose restart backendПерезапустить один сервис

Пример для реального проекта

Типичная архитектура веб-приложения:

version: '3.9'

services:
  # Веб-фронт на Nginx
  frontend:
    build: ./frontend
    ports:
      - "80:80"
    depends_on:
      - backend

  # API на FastAPI
  backend:
    build: ./backend
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/app
      - REDIS_URL=redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    volumes:
      - ./backend:/app

  # Фоновый воркер (та же база кода, другая команда)
  worker:
    build: ./backend
    command: python worker.py
    environment:
      - DATABASE_URL=postgresql://user:pass@db:5432/app
      - REDIS_URL=redis://cache:6379
    depends_on:
      - backend
      - db
      - cache

  # База
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: app
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user"]
      interval: 5s
      retries: 5

  # Кэш
  cache:
    image: redis:7-alpine

volumes:
  pgdata:

Тут пять сервисов. Одной командой docker compose up поднимается вся инфраструктура: фронт, бэк, воркер, база, кэш. Внутри — все связаны правильными URL.

Что НЕ надо делать

  • Хранить пароли прямо в файле. Через .env — правильно.
  • Открывать порт базы наружу. Только если правда надо для отладки.
  • Использовать latest в теге образа. Завтра обновится — сломается. Указывай конкретную версию: postgres:16.
  • Писать все сервисы в один. Если можно разделить — разделяй. Это и есть смысл Compose.

Compose vs Kubernetes

Docker Compose — для одной машины, локальной разработки или маленького сервера. Kubernetes — для больших продакшн-систем с десятками серверов.

Для 90% проектов Compose хватит с головой. Не беги в Kubernetes, пока не упрёшься в возможности Compose.

Итог

Docker Compose описывает несколько контейнеров в одном файле. Одна команда — весь проект. Volumes хранят данные, environment задаёт настройки, depends_on выстраивает порядок, healthcheck защищает от гонки при запуске. Стандарт для локальной разработки и небольших продакшн-развёртываний.
