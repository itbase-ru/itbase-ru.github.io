Next.js 15: что нового, App Router, Server Components

20 ноября 2026 • 13 мин чтения
Поделиться:

Next.js — это фреймворк на React, который к 2026 году стал де-факто стандартом для продакшна. Версия 15 принесла долгожданные улучшения: стабильный App Router, Server Components, Turbopack и новый API кеширования. Если ты фронтендер — это уже не «опция на будущее», а рабочий инструмент здесь и сейчас.

В этой статье — что нового в Next.js 15 простыми словами, как это использовать и какие грабли лежат по пути. Если React для тебя пока нов — начни с основ JavaScript. Без воды — только то, что реально поменяется в твоём коде.

App Router против Pages Router

В старом Next.js (до 13 версии) был Pages Router: каждый маршрут — это файл в папке pages/. Простая модель, но с ограничениями: layout нельзя было переиспользовать, nested-роуты были болью, data-fetching происходил через getServerSideProps.

В Next.js 15 App Router — стабильный и рекомендуемый. Теперь маршруты живут в папке app/, и каждый маршрут — это папка с файлом page.tsx. Layout-и объявляются в layout.tsx и автоматически оборачивают дочерние страницы. Loading.tsx, error.tsx, not-found.tsx — это всё файлы, которые автоматически подхватываются роутером.

Старый Pages Router всё ещё работает — не надо переписывать всё за раз. Новые проекты лучше делать на App Router, а старые мигрировать постепенно. Команда Vercel обещает поддерживать Pages Router ещё долго.

Главное архитектурное отличие App Router — layout-и вкладываются автоматически. У тебя может быть корневой layout (с шапкой и футером), в нём — layout секции (с сайдбаром), в нём — layout конкретной страницы. Это даёт переиспользование и не требует вручную оборачивать каждую страницу в одни и те же компоненты.

Также в App Router появился файл template.tsx — он похож на layout, но пересоздаётся при каждой навигации. Это полезно, когда ты хочешь сбросить состояние компонента при переходе между страницами. Например, форма поиска в хедере должна обнуляться при переходе на новую страницу — template.tsx делает это автоматически.

Server Components: серверный рендеринг нового поколения

Главное новшество Next.js 13+, и в 15-й версии оно доведено до ума. Server Component — это React-компонент, который рендерится на сервере и присылает в браузер готовый HTML. В браузер не попадает ни JSX, ни данные — только готовый DOM. Это уменьшает размер бандла и ускоряет первый paint.

По умолчанию в App Router все компоненты — серверные. Чтобы сделать компонент клиентским, нужно явно написать в начале файла:

'use client';

import { useState } from 'react';

export default function Counter() {
  const [n, setN] = useState(0);
  return <button onClick={() => setN(n + 1)}>{n}</button>;
}

Это разделение — главное архитектурное отличие нового Next. Серверные компоненты могут обращаться к БД напрямую, не тащут библиотеки в бандл, не имеют useState. Клиентские — те, где нужен интерактив: состояние, события, браузерные API.

Сравни: ты делаешь страницу товара. Информация о товаре — server component: тянется из БД, рендерится на сервере, клиенту приходит HTML. Кнопка «в корзину» — client component: нужно состояние, нужно событие. Они легко комбинируются.

Data fetching: теперь проще

В Pages Router для данных использовали getServerSideProps и getStaticProps — отдельные функции в каждом файле. В App Router — обычный async/await прямо в серверном компоненте:

async function getUser(id) {
  const res = await fetch('https://api.example.com/users/' + id);
  return res.json();
}

export default async function Page({ params }) {
  const user = await getUser(params.id);
  return <h1>{user.name}</h1>;
}

Fetch автоматически кешируется, и ты можешь управлять поведением через опции: { next: { revalidate: 60 } } — ревалидация раз в 60 секунд, { cache: 'no-store' } — всегда свежие данные. Это и есть новый API кеширования.

Также появился generateStaticParams для динамических маршрутов — он говорит Next.js, какие страницы сгенерировать статически на этапе сборки. Это особенно полезно для блогов и документации: ты заранее знаешь все URL, и Next сделает готовые HTML-файлы без запросов к БД в runtime. Сочетание generateStaticParams и ISR даёт гибкость: что-то статичное, что-то с ревалидацией, что-то серверное.

Turbopack: быстрая разработка

Turbopack — это новый bundler от Vercel, замена Webpack на dev. В Next.js 15 он стабильный для разработки и реально быстрее: холодный старт в 5-10 раз, hot reload почти мгновенный. Для продакшна пока рекомендуют Webpack, но и туда Turbopack скоро доберётся.

В больших проектах Turbopack даёт заметный буст: dev-сервер поднимается за секунды вместо минут, изменения видны сразу. Это особенно полезно, когда у тебя десятки страниц и сложная структура компонентов.

Что ещё важного

Streaming и Suspense: ты можешь показать часть страницы сразу, а тяжёлые части догружаются потом через Suspense-блоки. Это улучшает perceived performance — пользователь видит контент сразу, а не через 2 секунды.

Metadata API: вместо ручного управления head и meta-тегами — экспорт объекта metadata из компонента. Next сам собирает все мета-данные и собирает в правильном порядке.

Server Actions: вместо создания API-эндпоинтов для форм — пишешь async-функцию прямо в серверном компоненте, и она автоматически становится эндпоинтом. Удобно для мутаций.

Грабли и что не сделать так

Главная ошибка — сделать все компоненты клиентскими. Это убивает смысл Server Components и раздувает бандл. Старайся держать максимум на сервере, а в 'use client' переносить только листья с интерактивом.

Вторая ошибка — тащить в серверные компоненты библиотеки, которые работают только в браузере (например, те, что обращаются к window). Они сломаются на сервере. Такие части выделяй в отдельные клиентские компоненты.

Третья — полагаться на автоматическое кеширование, не зная, как оно работает. По умолчанию fetch кешируется надолго, и ты можешь получить устаревшие данные. Если данные должны быть свежими — явно отключай кеш. Подробнее про кеширование — в отдельной статье.

App Router — это не новый синтаксис. Это новая архитектура: сервер-клиентский контракт вместо клиентского SPA.

Деплой и хостинг: где крутить

Next.js можно захостить где угодно, но не любой хостинг раскроет все фичи. SSR, ISR, edge functions — это требует серверной среды, а не статичного файлового сервера. Разберём основные варианты.

Vercel — компания-создатель Next.js, их платформа — первый кандидат. Деплой сводится к git push: Vercel сам собирает, деплоит и раздаёт через CDN. Поддерживаются все фичи: ISR, Edge Functions, Image Optimization. Для хобби-проектов — бесплатно, для серьёзных — Pro за 20 USD/мес.

Self-hosted через Docker. Next.js можно собрать в Docker-образ и крутить где угодно: в облаке, на VPS, в Kubernetes. Важно: для SSR нужен Node.js-сервер, не статика. Образ собирается через next build и запускается через next start. Это даёт полный контроль, но требует настройки Nginx, SSL, мониторинга.

FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build
EXPOSE 3000
CMD ["npm", "start"]

Static export. Если у тебя полностью статичный сайт (блог, лендинг, документация), можно собрать Next.js в набор HTML/CSS/JS файлов через next export. Эти файлы раздаются любым статическим хостингом: GitHub Pages, Cloudflare Pages, Netlify. Минус — теряешь SSR, ISR, edge-функции. Только статика.

Cloudflare Pages. Альтернатива Vercel с акцентом на edge-сеть. Поддерживает Next.js через @cloudflare/next-on-pages. Бесплатно для большинства задач, но есть ограничения: не все Node.js API доступны на edge-runtime, библиотеки с fs или тяжёлыми зависимостями могут не работать.

AWS, GCP, Azure. Полная свобода, но и полная головная боль. Поднимаешь ECS/EKS или App Runner, деплоишь Docker-образ. Это выбор для больших компаний с DevOps-командой — для одиночек оверкилл. Подробнее про деплой и CI/CD — в статье про DevOps.

Главный совет: стартуй на Vercel, даже для коммерческих проектов. Когда упрёшься в лимиты или захочешь cost-optimization — мигрируй на self-hosted. Это займёт день-два, но только когда станет действительно нужно.

FAQ

Стоит ли мигрировать старый проект с Pages на App Router?

Если проект маленький — да, миграция займёт пару дней. Если большой — лучше начать новые страницы на App Router, а старые оставить. Vercel обещает поддержку Pages ещё долго, так что спешки нет.

Server Components заменят обычные React-компоненты?

Нет, они их дополняют. Server Components работают только в серверной среде (Next.js), а обычные React-компоненты — везде, включая SPA. Это просто новый инструмент, а не замена экосистемы.

Нужен ли Next.js, если у меня обычный SPA?

Если у тебя сложное приложение с SEO-страницами, блогом, лендингами — Next.js подходит идеально. Если у тебя админка без SEO — хватит Vite + React. Next.js — это про гибрид: можно часть страниц делать статичными, часть — серверными, часть — клиентскими.

Turbopack заменит Webpack полностью?

Со временем — да, но пока Turbopack стабилен только для dev. Для продакшн-бандла всё ещё рекомендуют Webpack. Vercel обещает полную стабильность Turbopack для prod в ближайших версиях.

Что лучше — Next.js или Remix?

Remix (ныне React Router 7) — отличная альтернатива с похожей философией. Next.js даёт больше «из коробки»: image optimization, ISR, edge functions. Remix фокусируется на веб-стандартах. Для большинства проектов Next.js — безопасный выбор.

Как быстро стартовать с Next.js 15?

Одной командой: npx create-next-app@latest my-app. Получишь готовый проект на App Router, TypeScript, Tailwind. Дальше — документация nextjs.org, она очень качественная. Через час сделаешь первую страницу.

Краткий вывод

Next.js 15 — это не революция, а эволюция: App Router стал стабильным, Turbopack быстрым, Server Components — нормой. Если ты на Pages Router — не обязательно перепрыгивать сегодня, но новые страницы лучше делать на App. Если начинаешь новый проект — бери 15-ю версию и не сомневайся.

Главное — не пытайся сразу использовать все возможности. Начни с базового роутинга и серверных компонентов, освой data fetching и кеширование, и только потом добавляй Server Actions, Streaming и Edge-функции. Эволюционный подход к изучению Next.js окупается: ты будешь понимать, что и зачем работает, а не копировать код из доки.
