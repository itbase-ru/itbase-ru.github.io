Что такое ORM — работа с базой через объекты

13 апреля 2026 • 10 мин чтения
Поделиться:

Когда пишешь код, работать с базой через SQL не всегда удобно. Строки запросов, ручное превращение данных в объекты, повторяющийся код. ORM решает это, позволяя общаться с базой как с обычными объектами Python или JavaScript.

Что такое ORM

ORM (Object-Relational Mapping) — это библиотека, которая превращает таблицы базы данных в классы, а строки — в объекты. Ты работаешь с объектами, а ORM сама генерирует SQL под капотом.

Пример сравнения. Одна и та же задача: найти пользователя по email.

Без ORM — чистый SQL

import sqlite3

conn = sqlite3.connect('app.db')
cursor = conn.cursor()
cursor.execute(
    'SELECT id, name, email FROM users WHERE email = ?',
    ('kirill@mail.ru',)
)
row = cursor.fetchone()
# row — это кортеж: (1, 'Кирилл', 'kirill@mail.ru')
# приходится вручную делать user = {'id': row[0], 'name': row[1], ...}

С ORM — обычные объекты

from sqlalchemy.orm import Session

user = session.query(User).filter(User.email == 'kirill@mail.ru').first()
# user — это объект класса User
print(user.name)   # обращаемся как к обычному атрибуту

Во втором случае ORM сама сгенерировала SQL, выполнила его и превратила результат в объект. Тебе остаётся работать с данными как с обычными Python-объектами.

Как это выглядит с моделями

В ORM ты описываешь таблицы через классы — они называются модели.

from sqlalchemy import Column, Integer, String
from sqlalchemy.orm import declarative_base

Base = declarative_base()

class User(Base):
    __tablename__ = 'users'   # имя таблицы в базе

    id = Column(Integer, primary_key=True)
    name = Column(String(100), nullable=False)
    email = Column(String(200), unique=True, nullable=False)

Этот класс описывает таблицу. По нему ORM поймёт, как создавать таблицу и как маппить строки в объекты.

Основные операции

Создать

user = User(name='Кирилл', email='kirill@mail.ru')
session.add(user)
session.commit()   # сохраняем в базу
print(user.id)     # ORM сама подставила id после вставки

Прочитать

# Все пользователи
users = session.query(User).all()

# Первый с таким email
user = session.query(User).filter(User.email == 'kirill@mail.ru').first()

# С сортировкой и ограничением
top = session.query(User).order_by(User.name).limit(10).all()

Обновить

user = session.query(User).get(1)
user.name = 'Кирилл Петрович'   # просто меняем атрибут
session.commit()                # ORM сама сделает UPDATE

Удалить

user = session.query(User).get(1)
session.delete(user)
session.commit()

Связи между таблицами

Одно из главных удобств ORM — связи. Вместо JOIN ты используешь обычные атрибуты.

from sqlalchemy import ForeignKey
from sqlalchemy.orm import relationship

class Order(Base):
    __tablename__ = 'orders'

    id = Column(Integer, primary_key=True)
    user_id = Column(Integer, ForeignKey('users.id'))
    total = Column(Integer)

    # ORM понимает: заказ принадлежит одному пользователю
    user = relationship('User', back_populates='orders')

class User(Base):
    __tablename__ = 'users'

    id = Column(Integer, primary_key=True)
    name = Column(String(100))
    email = Column(String(200))

    # А у пользователя много заказов
    orders = relationship('Order', back_populates='user')

Теперь можно работать так:

# Получить все заказы пользователя — без SQL, через атрибут
user = session.query(User).get(1)
for order in user.orders:
    print(order.total)

# Или наоборот — от заказа к пользователю
order = session.query(Order).get(10)
print(order.user.name)

ORM сама сделает JOIN и подгрузит нужные данные.

Плюсы ORM

  • Меньше кода. Не пишешь SQL руками — просто работаешь с объектами.
  • Защита от инъекций. ORM экранирует значения автоматически.
  • Не зависишь от СУБД. Один и тот же код работает с Postgres, MySQL, SQLite. Меняешь базу — код остаётся.
  • Типы и автодополнение. В редакторе видно поля модели.
  • Миграции. Многие ORM умеют обновлять схему базы автоматически.

Минусы ORM

  • Сложные запросы — боль. Аналитика с десятком JOIN на ORM превращается в кашу.
  • Проблема N+1. Если наивно пройтись по списку и обратиться к связанным объектам, ORM сделает отдельный запрос на каждого — сотни SQL-запросов вместо двух.
  • Скрытая магия. Не всегда понятно, какой SQL уходит в базу. Приходится включать логи.
  • Производительность. Иногда ORM-запрос в разы медленнее написанного вручную.
  • Порог входа. SQLAlchemy с её сессиями и relationships пугает новичков.

Проблема N+1

Классическая ловушка ORM. Показываю на примере.

# Наивно: получаем 100 заказов, потом у каждого спрашиваем пользователя
orders = session.query(Order).limit(100).all()
for order in orders:
    print(order.user.name)   # на каждой итерации — отдельный SQL-запрос
# Итого: 101 запрос к базе вместо 2

Решение — жадная загрузка. Заранее указываешь ORM, что нужно подгрузить связанные данные одним запросом:

from sqlalchemy.orm import joinedload

# Один JOIN вместо 101 запроса
orders = session.query(Order).options(
    joinedload(Order.user)
).limit(100).all()

for order in orders:
    print(order.user.name)   # уже загружено, никаких лишних запросов

Когда ORM не подходит

  • Сложные аналитические запросы. Если у тебя десяток JOIN и оконные функции — пиши SQL руками.
  • Высоконагруженные системы. ORM добавляет оверхед, и в hot-path это критично.
  • Задачи на миллионы строк. Тут важна каждая миллисекунда, ORM только мешает.
  • Скрипты на 20 строк. Проще сделать пару запросов через sqlite3, чем ставить SQLAlchemy.
ORM — инструмент, а не религия. В одном проекте можно использовать и ORM для CRUD, и чистый SQL для отчётов. Это нормально.

Итог

ORM превращает таблицы в классы и позволяет работать с базой как с обычными объектами. Убирает повторяющийся код, защищает от инъекций, даёт единый интерфейс к разным СУБД. Но у неё есть свои проблемы — N+1, скрытые запросы, сложности с аналитикой. Используй там, где она облегчает, и не бойся спускаться на уровень SQL, когда нужно.
