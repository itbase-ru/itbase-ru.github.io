Что такое Nginx и зачем он нужен на сервере

26 апреля 2026 • 10 мин чтения
Поделиться:

Когда ты открываешь любой крупный сайт — где-то на их сервере почти наверняка работает Nginx. Это самый популярный веб-сервер в мире, обогнавший Apache ещё в 2018 году. Разберёмся, что он делает и почему так популярен.

Что такое веб-сервер

Веб-сервер — программа, которая принимает HTTP-запросы и отдаёт ответы. Когда браузер открывает сайт, он обращается к веб-серверу на порт 80 или 443.

Nginx (читается «энджинкс») — один из таких серверов. Он умеет:

  • Отдавать статические файлы (HTML, CSS, JS, картинки).
  • Проксировать запросы к другим сервисам (Python, Node.js, Go).
  • Балансировать нагрузку между несколькими серверами.
  • Кэшировать ответы.
  • Терминировать HTTPS.
  • Сжимать трафик (gzip).

Зачем нужен Nginx, если уже есть приложение

Частый вопрос новичка: «У меня есть Django-сайт, он же и так работает — зачем мне Nginx?»

Ответ: приложение на Python — не веб-сервер. Оно умеет обрабатывать логику, но плохо справляется с:

  • Статикой. Django может отдать картинку, но это неэффективно. Nginx отдаёт файлы в разы быстрее.
  • HTTPS. Управление сертификатами — задача веб-сервера.
  • Медленными клиентами. Если клиент медленно читает ответ, Django будет ждать его. Nginx умеет буферизировать.
  • DoS-атаками. Nginx может ограничивать число запросов с одного IP.

Схема типичного проекта:

браузер → Nginx → Python-приложение
              ↓
           статика

Nginx стоит спереди. Если запрос на статику — отдаёт сам файл. Если на API — проксирует в приложение.

Reverse proxy

Ключевая роль Nginx в современном вебе — обратный прокси. Он принимает запросы от клиентов и передаёт их внутренним сервисам, а ответы возвращает клиенту.

Пример: у тебя три бэкенда на портах 8000, 8001, 8002. Снаружи открыт только Nginx на 80. Он маршрутизирует:

example.com/api/      → localhost:8000
example.com/admin/    → localhost:8001
example.com/static/   → папка /var/www/static

Клиент видит один домен. Внутри — три разных сервиса. Так строятся почти все крупные проекты.

Балансировка нагрузки

Когда один сервер не справляется — запускают несколько. Nginx распределяет запросы между ними.

upstream backend {
    server 10.0.0.1:8000;
    server 10.0.0.2:8000;
    server 10.0.0.3:8000;
}

server {
    location / {
        proxy_pass http://backend;
    }
}

Способы балансировки:

  • round-robin — по очереди. По умолчанию.
  • least_conn — на сервер с меньшим числом активных соединений.
  • ip_hash — один клиент всегда попадает на один и тот же сервер.

Установка

# Ubuntu / Debian
sudo apt update
sudo apt install nginx

# Запуск и автозагрузка
sudo systemctl start nginx
sudo systemctl enable nginx

# Проверка статуса
sudo systemctl status nginx

После установки Nginx сразу отдаёт приветственную страницу на http://localhost.

Структура конфигов

/etc/nginx/
├── nginx.conf               # основной конфиг
├── sites-available/         # доступные сайты
│   ├── default
│   └── myapp.conf
├── sites-enabled/           # включённые сайты (симлинки)
└── conf.d/                  # доп. конфиги

Типичный процесс: создаёшь конфиг в sites-available, делаешь симлинк в sites-enabled, перезагружаешь Nginx.

Пример конфига для статики

server {
    listen 80;
    server_name example.com www.example.com;

    # Папка со статикой
    root /var/www/mysite;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }

    # Логи
    access_log /var/log/nginx/example_access.log;
    error_log  /var/log/nginx/example_error.log;
}

Что тут:

  • listen 80 — слушать порт 80 (HTTP).
  • server_name — для какого домена конфиг.
  • root — корневая папка с файлами.
  • index — файл по умолчанию.
  • try_files — попробовать файл, потом папку, иначе 404.

Пример конфига с проксированием

Допустим, у тебя Django/FastAPI/Flask на порту 8000, и ты хочешь отдавать статику напрямую через Nginx:

server {
    listen 80;
    server_name example.com;

    # Статику отдаём сами — это быстро
    location /static/ {
        alias /home/user/myapp/static/;
        expires 30d;
    }

    # Медиафайлы (загруженные пользователями)
    location /media/ {
        alias /home/user/myapp/media/;
    }

    # Всё остальное — проксируем в приложение
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

Заголовки X-Forwarded-* важны: приложение через них узнаёт настоящий IP клиента, а не IP Nginx.

HTTPS через Let's Encrypt

Раньше сертификаты стоили денег и настраивались вручную. Сейчас всё делается в две команды:

# Установить certbot
sudo apt install certbot python3-certbot-nginx

# Получить сертификат и автоматически настроить Nginx
sudo certbot --nginx -d example.com -d www.example.com

Certbot сам:

  • Проверит, что домен указывает на этот сервер.
  • Получит сертификат.
  • Перепишет конфиг Nginx для HTTPS.
  • Настроит автопродление каждые 90 дней.

После этого сайт работает по https:// без ручной возни.

Полезные команды

КомандаЧто делает
nginx -tПроверить синтаксис конфигов
nginx -s reloadПерезагрузить без разрыва соединений
systemctl restart nginxПолный перезапуск
systemctl status nginxСтатус сервиса
tail -f /var/log/nginx/access.logСмотреть запросы в реальном времени
tail -f /var/log/nginx/error.logСмотреть ошибки

Правило: перед каждым reload делай nginx -t. Если конфиг с ошибкой — Nginx не запустится, и сайт упадёт.

Nginx vs Apache

КритерийNginxApache
АрхитектураСобытийнаяПроцесс/поток на запрос
Под нагрузкойДержит тысячи соединенийТребует больше памяти
СтатикаОчень быстроМедленнее
КонфигиЛаконичныеБолее гибкие, но сложнее
.htaccessНетЕсть

Nginx выигрывает по скорости и по нагрузке. Apache — по гибкости конфигурации и старой экосистеме. Для новых проектов чаще берут Nginx.

Итог

Nginx — веб-сервер, который стоит перед приложением и делает всю «грязную работу»: HTTPS, статика, проксирование, балансировка. Почти любой серьёзный проект использует его. Конфиги лаконичные, управление через systemctl, HTTPS — через Certbot в две команды. Если разворачиваешь сайт на своём сервере — Nginx будет первым, что ты поставишь.
