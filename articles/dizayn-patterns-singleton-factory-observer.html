Дизайн-паттерны — Singleton, Factory, Observer

23 апреля 2026 • 11 мин чтения
Поделиться:

Дизайн-паттерны — это готовые решения типовых задач. Не библиотеки, не код, который копируют, а шаблоны мышления: увидел знакомую проблему — вспомнил проверенное решение. Разберём три самых частых.

Что такое паттерн

Паттерн — это описание того, как решать определённый класс задач. Появились они в 1994 году в книге «Design Patterns» (её называют «бандой четырёх» — GoF). С тех пор — стандарт индустрии.

Не путай с алгоритмами: алгоритм — конкретные шаги решения. Паттерн — структура кода, которую можно применить к разным задачам.

Паттерны — не цель, а инструмент. Не надо пихать их везде. Но не знать их — значит изобретать велосипед.

Паттерн 1. Singleton (Одиночка)

Задача: нужен объект, который существует в единственном экземпляре на всю программу.

Примеры:

  • Подключение к базе данных — не нужно создавать новое на каждый запрос.
  • Конфигурация приложения.
  • Логгер.
  • Кэш в памяти.

Реализация на Python

class Database:
    _instance = None   # храним единственный экземпляр

    def __new__(cls):
        # Если экземпляр ещё не создан — создаём
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        # Всегда возвращаем один и тот же объект
        return cls._instance

    def query(self, sql):
        return 'Результат запроса: ' + sql

# Проверяем — оба раза один и тот же объект
db1 = Database()
db2 = Database()

print(db1 is db2)   # True

Первый вызов создаёт объект. Второй, третий, десятый — возвращают тот же самый. Вся программа работает с одним подключением.

Плюсы и минусы

ПлюсыМинусы
Один объект — экономия ресурсовГлобальное состояние — сложно тестировать
Единая точка доступаСкрытые зависимости в коде
Контроль над состояниемПроблемы с многопоточностью

Singleton часто критикуют: он превращается в «глобальную переменную» и усложняет тесты. Используй его там, где правда нужен один объект — например, для подключения к базе.

Паттерн 2. Factory (Фабрика)

Задача: создавать объекты, не указывая в коде их точный класс. Логика создания — в одном месте.

Пример: приложение поддерживает разные способы оплаты. В зависимости от выбора пользователя — создаётся нужный объект.

Без паттерна — куча условий

def process_payment(method):
    if method == 'card':
        payment = CardPayment()
        payment.pay()
    elif method == 'paypal':
        payment = PaypalPayment()
        payment.pay()
    elif method == 'crypto':
        payment = CryptoPayment()
        payment.pay()
    # И так везде, где нужна оплата

Если добавится новый способ — придётся искать все такие места в коде.

С паттерном — единая точка

# Базовый класс — общий интерфейс
class Payment:
    def pay(self, amount):
        raise NotImplementedError

# Конкретные реализации
class CardPayment(Payment):
    def pay(self, amount):
        return 'Оплата картой: ' + str(amount) + ' руб.'

class PaypalPayment(Payment):
    def pay(self, amount):
        return 'Оплата через PayPal: ' + str(amount) + ' руб.'

class CryptoPayment(Payment):
    def pay(self, amount):
        return 'Оплата криптой: ' + str(amount) + ' руб.'

# Фабрика — единственное место с логикой выбора
class PaymentFactory:
    @staticmethod
    def create(method):
        if method == 'card':
            return CardPayment()
        elif method == 'paypal':
            return PaypalPayment()
        elif method == 'crypto':
            return CryptoPayment()
        else:
            raise ValueError('Неизвестный метод: ' + method)

# Использование
payment = PaymentFactory.create('card')
print(payment.pay(1500))

Теперь добавление нового метода оплаты — это правка только в одном месте — в фабрике.

Когда использовать

  • Создание объектов с разной логикой.
  • Выбор класса во время выполнения.
  • Скрыть от пользователя детали создания.

Паттерн 3. Observer (Наблюдатель)

Задача: одни объекты должны узнавать об изменениях других — не будучи жёстко связанными с ними.

Примеры:

  • Уведомления: изменился заказ — отправить письмо, push, сообщение в чат.
  • UI: изменилась модель — обновились все компоненты.
  • События в браузере: клик, скролл, ввод.

Реализация

class Publisher:
    'Издатель — источник событий'

    def __init__(self):
        # Список подписчиков
        self._subscribers = []

    def subscribe(self, callback):
        # Кто-то подписывается на события
        self._subscribers.append(callback)

    def unsubscribe(self, callback):
        # Отписка
        self._subscribers.remove(callback)

    def notify(self, event):
        # Уведомляем всех подписчиков
        for callback in self._subscribers:
            callback(event)

# Создаём издателя
shop = Publisher()

# Подписчики — обычные функции
def send_email(event):
    print('Отправляем email о событии: ' + event)

def send_push(event):
    print('Отправляем push: ' + event)

def log_event(event):
    print('Пишем в лог: ' + event)

# Подписываемся
shop.subscribe(send_email)
shop.subscribe(send_push)
shop.subscribe(log_event)

# Произошло событие — все узнают
shop.notify('Новый заказ #42')

Издатель не знает, кто на него подписан. Он просто кричит «событие!» — а подписчики реагируют каждый по-своему. Плюс в том, что подписаться можно в любой момент, а издатель об этом узнает автоматически.

Observer в браузере

Ты используешь его каждый день — это addEventListener:

// Кнопка — издатель
var button = document.querySelector('#buy');

// Подписчики — функции-обработчики
button.addEventListener('click', function() {
  console.log('Отправляем заказ');
});

button.addEventListener('click', function() {
  console.log('Показываем уведомление');
});

// Один клик — все подписчики сработают

Когда использовать

  • Событийная модель: одно событие → много реакций.
  • Слабая связанность: объекты не знают друг о друге.
  • Динамические подписки: кто-то может подписаться или отписаться в любой момент.

Три паттерна вместе

В реальном проекте они часто комбинируются:

  • Singleton — единый логгер приложения.
  • Factory — создание подключений к разным сервисам.
  • Observer — событийная шина: компоненты публикуют события, другие подписываются.

Другие паттерны — коротко

Всего паттернов больше 20. Вот те, о которых стоит знать:

ПаттернЗачем
AdapterПревратить один интерфейс в другой
DecoratorДобавить поведение без изменения класса
StrategyПереключать алгоритмы на лету
RepositoryАбстракция над базой данных
MVCРазделить модель, представление и контроллер

Не увлекайся

Есть шутка: «Начинающий программист применяет паттерны везде. Опытный — знает, когда не применять».

Паттерны нужны там, где они реально упрощают код. Если Singleton добавляет сложности, а Factory решает задачу на 5 строк — лучше без них.

Правило: сначала пиши простой код, потом замечай повторяющиеся проблемы и применяй подходящий паттерн. Не наоборот.

Итог

Singleton — один объект на всю программу. Factory — централизованное создание объектов с выбором класса. Observer — подписка на события, слабая связанность. Все три встречаются в реальном коде постоянно. Изучить их стоит — но применять только тогда, когда это упрощает, а не усложняет.
